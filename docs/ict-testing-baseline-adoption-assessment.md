# ICT Testing Baseline — Gap Analysis & Adoption Assessment

**At assessment time (2026-08-12, pre-adoption), the answer to "do we support ICT Testing Baselines" was: no.** Zero mentions of the baseline, Trusted Tester, or the Access Board existed in the bundle (verified by repo-wide search that day). What exists is a thin Section 508 *context* layer from the Vital-Core adoption — the `section_508_fpc_context` field and the "map 508 web conformance to WCAG 2.0 A/AA, never overstate 2.2-only findings" boundary rule — with no test-process vocabulary behind it.

**Decision: adopt in three tiers.** **Tier 1 (first commits after the Phase 0 gate, docs only):** name the baseline in the existing Section 508 boundary sections so the bundle stops being silent about the federal test-completeness standard its 508 field implies. **Tier 2 (behind a verify-the-source gate):** make Revised Section 508 engagements first-class at audit scope — a federal profile in the planner's AUDIT-SCOPE MODE, an honest baseline-coverage crosswalk in `a11y-test`, and an optional baseline-test citation on findings. **Tier 3 (defer/watch):** the Electronic Documents baseline beyond a boundary declaration, ANDI tooling, the planned software/hardware baselines, and anything resembling Trusted Tester certification claims. The baseline slots into the audit-scope layer *beside* WCAG-EM, not on top of it: WCAG-EM answers "how do you structure an evaluation," the baseline answers "what minimum tests must a Section 508 conformance test process include." Those are orthogonal, and the bundle currently teaches only the first. **Why now:** owner-directed adoption (2026-08-12) plus federal-market positioning — a growing share of this bundle's audience speaks Trusted Tester/baseline as its native testing vocabulary. The justification is recorded deliberately: if federal positioning is deprioritized before Phase 2 begins, Phase 2 converts to trigger-gated (first declared-Section-508 engagement) without revisiting this assessment.

Assessed 2026-08-12 from primary fetches of the live portfolio site (landing page, both all-tests pages), the `atbcb/ICTTestingBaseline` GitHub repository (releases, LICENSE, `_baselines` source tree), and section508.gov/DHS pages via search. **Phase 0 executed 2026-08-12** (this document corrected in place — every claim, not only the *(verify)*-marked ones, the WCAG-EM discipline): the verified reference is [`ict-testing-baseline-reference.md`](ict-testing-baseline-reference.md) and the machine-readable ID ground truth is [`ict-baseline-test-id-manifest.yaml`](ict-baseline-test-id-manifest.yaml) — 24 families / **62 active web tests**, **57 documents tests**, provisional hand classification 36 tool-assisted / 23 judgment-only / 2 machine-evaluable / 1 always-passes. The gate is open; Tiers 1–3 are unblocked. **Critic gate executed 2026-08-12 (proposal-critic, verdict REVISE, corrections applied throughout):** the critic pass independently raw-fetched the complete published web test list (~214KB, whole — the drafting session's truncation was its fetch summarizer, not the server), read the full LICENSE, and pulled upstream commit and branch history; its findings fixed the published enumeration (families 1–24), the license citation condition, the live site-vs-tag divergence and pin rule, the ACR boundary, and the 508-scope gate definition below.

## What It Is

The **ICT Testing Baseline Portfolio** (`ictbaseline.access-board.gov`) establishes the minimum set of test components a Section 508 conformance test process must include. Lineage: authored under the Federal CIO Council's Accessibility Community of Practice (ACOP), now maintained by the **ICT Testing Baseline Working Group (ITBWG)** with the site hosted by the U.S. Access Board (contact `ictbaseline@gsa.gov`). The Web baseline is recognized as a Best Practice by the ACOP. The GitHub repository is active — repo-level push 2026-08-09 (a working branch; `main` HEAD is `6c537a3b`, 2026-07-24).

Two baselines are published:

- **ICT Testing Baseline for Web v3.1** — GitHub release 2024-04-01 (prior: v3.0 2020, v3.0.1 2021). **The live site is ahead of the tag:** it builds from `main` (no gh-pages branch), which carries post-tag content commits through 2026-02-05 (the documents-baseline Appendix A 18.A addition #570, typo/heading fixes #561, an H44 link fix #534, plus the flat→`web-baselines/`+`document-baselines/` restructure), while the site still self-labels "version 3.1." Site-vs-tag divergence is the *current state*, not a risk — which is why Phase 0 pinned `main` @ `6c537a3b` (2026-07-24), never the tag.
- **ICT Testing Baseline for Electronic Documents v1.0** — landing page: "Version 1.0 (published September 30, 2024)". **Verified at the pin: no GitHub release or tag exists for it** — document versions are cut on `main`, which strengthens the SHA-pin rule.

Software and hardware baselines are stated as planned, not published.

**Structure.** Numbered test families, each containing lettered tests with stable IDs of the form `1.A-KeyboardAccess`, `5.C-ControlState`, `10.G-ErrorPrevention`. The published web list enumerates **families 1–24** — Focus consolidated at family 2 (`2.A-FocusVisible`, `2.B-FocusOrder`, `2.C-OnFocus`), Non-Interference at `3.A` — confirmed by a complete raw fetch of `/allwebbaselines.html` during the critic pass; no family 25 exists on the site. The source tree carries renumbering artifacts (`03FocusOrder.md`, `25Noninterference.md` — title-less tombstones that the all-tests page's include-by-title assembly never renders): the published list, never the file list, is the citable enumeration. Phase 0 characterized the page's internal irregularities exactly (the drafting-session descriptions were imprecise): `18.A` is a **retired stub** — it redirects to `6.B`, declares no test ID, and its heading carries an upstream typo — and `21.C-AutoUpdate`'s Results sentence cites the invalid `21.B-AutoUpdate`; the declared ID is always authoritative (manifest: `invalid_id_strings_on_published_pages`). The documents baseline does **not** mirror families 1–24: 23 sections and 57 declared tests, with family 19 (Frames) present only as an N/A note, families 4 and 23 retained-but-empty under the E205.4 exception, `6.C-Captcha` declared yet marked not applicable, documents-specific IDs (`11.A-DocumentTitled`, `15.A-LanguageDocument`, `15.B-LanguageParts`, `18.A-MeaningfulContent`, `18.B-MeaningfulSequence`), and its own stale-Results-line defects. Beyond the tests, the load-bearing *published* assets are the **Appendix A cross-reference tables** (instruction-level SC/508 map — the real crosswalk seed) and the Appendix B changelogs. Two assets the drafting session over-weighted are repo-only (404 on the live site): `00WCAG-Applicability.md` is the E207.2.1 word-substitution note, not an applicability matrix, and `DevelopTestProcess.md` is legacy v2-era how-to text — the published introduction carries the alignment rules.

**Standards mapping — and its trap.** Revised Section 508 incorporates WCAG 2.0 Level A/AA. The baselines map to Section 508 (and therefore WCAG 2.0) while *citing WCAG 2.2 Understanding articles for clarity*. That is a designed-in version skew: a 2.2 citation in baseline text is a reading aid, never a 2.2 conformance mapping. This is the same reading-discipline class as the KAT `conformance_level` lesson (upstream issue #27) — a field/citation that looks like one semantic and carries another. Source-confirmed in Phase 0, with two additions: family 17's tests cite the non-WCAG 508 provisions 503.4/503.4.1/503.4.2 (the introduction's 415.1.x cites are the hardware-chapter analogues — cite 503.4.x when citing what the tests test), and `24.A-Parsing` **always passes** by upstream design ("No testing necessary," WCAG 2.0 Errata 13) with markup consequences re-routed to other SCs.

**Baseline ≠ test process.** The baseline defines *what* must be tested; test processes define *how*. DHS **Trusted Tester v5** is "an ICT Baseline-aligned" manual test process — the dominant federal implementation, with certification courses at v5.1.3 (April 2024). Alignment of a process to the baseline is an evaluable property (the `DevelopTestProcess` guidance); certification of humans is DHS's.

**License.** MIT-style 2018 grant from the Federal CIO Council ACOP — use/copy/modify/publish rights, AS-IS, but **conditional**: the ACOP must be cited as the originating source, including the URL, and — second verified condition — modifications must **not** be attributed to ACOP. Any committed reference or extract therefore carries that citation, and the manifest marks its classification fields as this repo's additions. Licensing would permit vendoring; the house prompt-only boundary still forbids it (same ruling as Vital-Core, keyboard-a11y-tester, WCAG-EM).

## Where the Bundle Already Aligns

Honesty first — the substance is mostly here; the vocabulary is entirely absent:

- **The 508 boundary already exists.** `docs/a11y-evidence-finding-contract.md` §"Section 508 and WCAG Boundary" and the Vital-Core assessment already rule: WCAG 2.2 AA is the bundle's target, 508 maps to WCAG 2.0 A/AA, never label 2.1/2.2-only criteria as 508 failures. The baseline work *extends* this rule; it does not invent it.
- **The audit process layer exists.** AUDIT-SCOPE MODE (WCAG-EM five steps), the evaluation-report contract, and the sampling discipline are the skeleton a 508 audit hangs on. WCAG-EM deliberately does not define a minimum test set; the baseline is exactly that missing dimension for federal scope.
- **The measurement lanes already test most web-baseline substance.** Keyboard access and trap families (1.x) via Playwright real-key rules and keyboard-a11y-tester; focus visibility/order (2.x) including the bundle's only machine evidence for focus-indicator sufficiency; name/role/state/value (5.x) via virtual-screen-reader and axe; contrast, forms, tables, structure, page titles, language, media — capability exists, baseline vocabulary doesn't.
- **bug-reporting is already TT-shaped.** Its required fields (URL, XPath, snippet, SC, rule ID, severity, frequency, reproduction) are what a Trusted Tester–reproducible finding needs.
- **Severity ⊥ conformance is already law here.** The WCAG-EM adoption fixed this dimension pair; baseline outcomes join the conformance side unchanged.

## Gap Analysis — What the Baseline Ecosystem Expects That the Bundle Lacks

1. **No baseline vocabulary at all.** A federal engagement asking "which ICT Baseline tests does your test process cover?" — the standard procurement/QASP framing — gets silence. This, concretely, is what "we don't support it" means.
2. **The planner asks "Section 508?" and teaches nothing federal.** Phase 1's compliance-target question names Section 508 (SKILL.md line 207) but no protocol content covers: conformance floor selection (WCAG 2.0 A/AA + the non-WCAG 508 provisions), or declaring the 2.2-vs-2.0 delta a 2.2-AA-default bundle owes a 508 engagement in *both* directions. Concrete trap: 4.1.1 Parsing — removed in WCAG 2.2, formally present in 508's 2.0 basis, and baseline test `24.A-Parsing` exists. **Resolved in Phase 0:** the test's published instructions are "No testing necessary" and its result is "Baseline Test 24.A-Parsing passes" (WCAG 2.0 Errata 13), with real markup consequences re-routed to other SCs by the test's own Limitations text. The delta declaration therefore teaches *why it auto-passes*, not to test it; the residual failure modes are a reviewer re-litigating parsing or dropping the re-routing.
3. **No coverage crosswalk.** Nothing maps baseline test → a11y-test execution mode → evidence artifact, with honest NOT-COVERED rows for manual-only test conditions. The false-coverage honesty discipline from `test-hybrid-product-audit` (agreeing the web stack covers what it cannot fails the plan regardless of other quality) is the house pattern to reuse — the crosswalk is where it becomes checkable for federal scope.
4. **Findings can't carry a baseline citation.** Neither the evidence-finding contract nor bug-reporting has a field for the baseline test ID a federal reviewer would file under.
5. **The Documents baseline is out of measurable scope and nothing says so.** The measurement stack is web-only; PDFs and Office documents are exactly the transit-portal-q3 boundary trap. Declare the boundary (mirroring the WCAG-EM non-web ruling); do not imply coverage.
6. **No eval instrument.** Nothing grades 508-scope framing, and baseline test IDs are precisely the exact-ID class local models fabricate (the qwen3.6:35b bug-report caveat: perfect structure, fabricated selectors/IDs). An output citing `5.C-ControlState` that no one verified is worse than one citing nothing.

## Gap Analysis — What the Bundle Has That the Baseline Doesn't Cover

Adopting the baseline must not erode these:

- **Design-phase lifecycle.** The baseline evaluates ICT that exists. The planner/critic-on-plans half of the lifecycle is out of its scope entirely — same negative space as WCAG-EM, same differentiator.
- **Impact severity.** Baseline/TT outcomes are conformance-oriented pass/fail with no user-impact severity model. CRITICAL/MAJOR/MINOR/ENHANCEMENT stays orthogonal — report both, derive neither.
- **The WCAG 2.2 AA default target.** The baseline floor is 2.0/508. A federal profile *adds a floor and a delta declaration*; it never lowers the bundle's default target. Recommending 2.2 AA remediation while reporting against the 2.0 floor is the correct dual posture, and outputs must keep the two visibly separate.
- **Perspective/role audits, APG component depth, evidence-contract discipline** (fingerprints, trend language) — no baseline equivalent; a baseline-scoped report from this bundle should be more evidence-rigorous than the baseline requires, not less.
- **Non-federal regulatory adjacency stays out.** "Government accessibility" ≠ Revised 508: ADA Title II (DOJ 2024 rule) references WCAG 2.1 AA with first compliance deadlines in 2026 *(verify exact cites if ever adopted)* and EN 301 549 is its own regime. The federal profile means Revised Section 508 specifically; one boundary sentence prevents the conflation, and adopting those regimes is explicitly not part of this plan.

### Phase 4a — The ANDI spike (specified 2026-09-03; not yet run)

The defer above has sat on "unvalidated" since 2026-08-12 without saying what validation would look like, which makes it un-actionable and lets the item drift indefinitely. This specifies the probe so the defer can actually resolve in one direction or the other. Following the house pattern: a time-boxed probe with kill criteria, **not** a full assessment — a full assessment is what happens *if* the probe passes.

**What ANDI is.** A bookmarklet from SSA's Accessible Solutions Branch ([install](https://www.ssa.gov/accessibility/andi/help/install.html), [source](https://github.com/SSAgov/ANDI), open source) that inspects accessible names, descriptions, roles, states, and structural relationships in a live page. It is the tool the DHS Trusted Tester process is taught and conducted with, which is why federal reviewers ask for it by name.

**There are two ANDI questions, and they have different answers. Keep them apart.**

**Q1 — ANDI as an automated evidence producer.** *Does injecting ANDI and scraping its output produce evidence this stack cannot already produce, on baseline tests currently marked not-covered or partial in the [crosswalk](../.claude/skills/a11y-test/references/ict-baseline-crosswalk.yaml)?* This is what the probe below tests, and the expected answer is no.

**Q2 — ANDI as the instrument in a guided human verification pass.** Raised 2026-09-03 and **not** answered by the probe below. A VPAT/ACR chain structurally requires human verification: `acr-reporting` emits a draft a person signs, `a11y-content-judgment` refuses any row without a name in `ratified_by`, and the [fix-closure contract](a11y-fix-closure-contract.md) states what must be true at closure. At the *fixed* stage especially, somebody has to walk the pages and confirm the fix on the real thing.

Q2 inverts one of the kill criteria below, and the inversion is the point. "The delta is judgment, not data" disqualifies ANDI as an automated lane — and at a verification stage judgment *is* the deliverable, so the same property becomes the fit. ANDI is also the inspector federal reviewers already know by name, which matters when the artifact is a conformance claim somebody has to defend.

**But Q2's gap is a missing stage, not a missing tool.** This bundle has no guided-verification surface. The fix-closure contract says *what must hold* at closure without saying *how a person establishes it*, and nothing in the lifecycle walks a human through per-page confirmation. Adopting ANDI before that stage exists would be a tool in search of a workflow. Sequencing: **define the verification stage first** — what a person confirms per finding, in what order, recorded how, ratified by whom, following the draft-then-ratify shape `a11y-content-judgment` already establishes — **then ask which instrument helps them do it.** ANDI is a strong candidate for that slot; it is not a substitute for specifying it.

Q2 is unscoped work, recorded here so it does not evaporate. It neither gates nor is gated by the Q1 probe.

**The Q1 probe, specified.**

**Time box:** half a day. If it runs long, that is itself a result — the routing cost exceeds the evidence value.

**Method.**
1. Pick 3 baseline tests from the crosswalk's not-covered/partial rows where ANDI's inspection surface plausibly applies, and 1 covered row as a control.
2. Inject ANDI into a page under test via Playwright, and capture its output programmatically rather than by screenshot.
3. For each of the 4, produce the same evidence with the modes already routed here (axe-core, keyboard-a11y-tester, virtual-screen-reader, `page.accessibility.snapshot()`).
4. Diff. The deliverable is the delta, not a demo.

**Kill criteria — any one of these ends it as a defer, permanently or until a named trigger fires:**
- **No delta.** Every not-covered/partial row ANDI addresses is already producible by a routed mode. This is the likeliest outcome and the most valuable one to have on the record.
- **Output is not machine-readable without scraping rendered DOM.** ANDI is built to be read by a person. If the only way to get its results is parsing its own injected UI, the evidence is fragile against any upstream change and the maintenance cost lands on us.
- **The delta is judgment, not data.** If what ANDI adds is *a human reading its output and deciding*, then automating the injection produces another data dump and the detector-not-a-verdict-authority rule applies unchanged. That is not a reason to adopt; it is a reason the manual protocol stays where it is.
- **Licence or distribution blocks routing.** Confirm before, not after.

**Pass criterion (all three, not any):** a machine-readable delta, on at least one currently not-covered baseline row, that no routed mode produces. Anything less leaves the defer standing.

**What passing would earn:** a full adoption assessment, on the standard form. Not adoption.

**Prior on the Q1 outcome, stated up front so the probe cannot be graded generously after the fact:** the crosswalk's not-covered rows are not-covered mostly because they need human or real-AT judgment, not because they need a better inspector. The expected result is *no delta* — an argument against Q1 and, read carefully, an argument *for* taking Q2 seriously. Recording it clearly is worth the half day — it converts a standing "we should probably look at ANDI" into a closed question with a reopen trigger.

**Correlated-dependency note.** ANDI and YANKI are the same SSA branch. Adopting both is one bet, not two — the same reasoning already applied to `@guidepup/guidepup` and virtual-screen-reader sharing a maintainer. YANKI's technique is documented in `a11y-test` (attribute-removal differential diagnosis) with no dependency routed, which is the shape to prefer here too if the ANDI probe ever passes.


## Risks & Uncertainty

- **Live-standard drift is the top hazard.** Upstream ships content to `main` (repo push 2026-08-09 on a working branch; `main` content commits through 2026-02-05) while the site self-labels a 2024 version, and three working branches signal a 3.x successor plus a site reorg. A tag-pinned reference would carry a false identity on day one; the SHA pin, push-triggered recheck, and archive anchors exist for exactly this.
- **Phase 0 verification landed 2026-08-12; one residual.** Per-test enumeration, mappings, anomalies, and the non-WCAG provisions extract are source-verified (see the reference doc), and the Wayback snapshots were confirmed via the CDX API later the same day (timestamps 20260812143029 / 20260812143044). Residual: the site can drift ahead of the pin at any time — the recheck triggers exist for exactly this.
- **Version-skew misreads.** The baseline citing WCAG 2.2 Understanding while mapping to 2.0/508 will be misread as 2.2 coverage by default — by models and humans. The reference doc must state it; the planner profile must restate it.
- **Exact-ID fabrication.** Baseline IDs join XPaths and rule IDs in the class of values local models invent fluently. No generation routing without the Phase 3 value-check; hand-verify the crosswalk.
- **Checklist creep.** The failure mode of adopting a federal test standard is baseline citations metastasizing into every review. The gate is declared 508 scope; outside it, a baseline citation is dead output and reviewers should treat it as a finding.
- **Certification honesty.** "Baseline-aware," "TT-reproducible in form," "designed to cover" — yes. "Baseline-conformant," "Trusted Tester certified" — never, absent an external review that has actually happened.
- **Regulatory adjacency.** ADA Title II and EN 301 549 pressure will tempt scope drift into "one federal profile for everything government." Resist; they are different regimes with different WCAG versions.

## What This Does Not Claim

- Not a capability to test PDFs, Office documents, native software, or hardware — the Documents baseline is a declared boundary, not a roadmap item.
- Not an ACR/VPAT generator: the federal annex aggregates evidence for whoever authors the Accessibility Conformance Report; it is not itself one.
- Not Trusted Tester certification, simulation of the TT course, or any conformance badge for the bundle's own test process.
- Not a change to the WCAG 2.2 AA default target, the severity scale, the critic's protocol, or the perspective/role taxonomies.
- Not a claim that the bundle is baseline-aligned today — the crosswalk exists to find out honestly, and its NOT-COVERED rows are the deliverable, not an embarrassment.
- Not legal advice; Section 508 conformance determinations remain the agency's.
