# Accessibility Design Critique — BlogPost Component

## Phase 0 — Evidence Intake

Two artifacts are in evidence: an axe-core scan (`.../axe-batch-2026-08-25/013-127-0-0-1-8777-heading-hierarchy-skipped-html.json`) and a keyboard-a11y-tester screen-reader reading-order census (`.../heading-hierarchy-skipped-kat-census/sr-census.json`). Both are machine-detectable/structural evidence. Per the evidence digest's own scoping, neither artifact is the prescribed instrument for interaction defect classes — `keyboard-operability` needs a real-keyboard Playwright transcript, `focus-order-indicator` needs a KAT driven focus trace, `name-role-state` (ARIA-state-change announcement) needs virtual-screen-reader assertion output. None of those three were supplied. This review therefore treats structural findings (heading order, landmark presence) as measured fact, and treats keyboard/focus/state claims as bounded by source-code reading only, explicitly flagged as design reasoning rather than measurement wherever they appear below.

One piece of measured corroboration is useful here: the KAT census recorded zero interactive-role entries across all 33 entries (only document/article/heading/paragraph/list/listitem roles appear). That doesn't prove keyboard operability one way or the other, but it does corroborate — as a measured fact, not just a read of the JSX — that this component renders no interactive controls at all, which is why Phases 3–5 below come back clean/not-applicable rather than "unverified."

The axe `region` rule's `tags` array includes `"cat.keyboard"` alongside `"best-practice"`. This is axe's internal rule-taxonomy label, not a record of any keyboard interaction being tested, and it is not treated as keyboard evidence anywhere in this review.

## Pre-commitment Predictions

Before working through the checklist phases, based on this being a static long-form content/article component (not a widget, form, or dynamic region):

1. Heading hierarchy will skip a level, likely driven by visual sizing rather than content structure.
2. The component's root landmark (`<article>` only) may not be wrapped in `<main>` depending on how it's mounted — worth checking, but this is a "depends on host page" prediction, not a certainty.
3. A component with no interactive elements should come back clean on ARIA pattern, focus management, and state communication — these phases are predicted to be N/A rather than "no findings from investigation."
4. The self-reported checklist item "No headings for visual styling only" is a claim worth testing against the actual heading/CSS pairing, not accepting at face value.
5. Long-form multi-section content like this is a case where screen-reader users commonly navigate by heading level — so a heading-order defect here carries more real navigational weight than the same defect would in a short page.

## Investigation Notes (Phases 2–7)

**Phase 2 — Semantic HTML Audit.** No interactive elements exist anywhere in the component (no buttons, links, inputs, or ARIA-role substitutes for them) — confirmed both by reading the JSX and by the KAT census's zero-interactive-role result. There is no case of ARIA masking bad semantics because there is effectively no ARIA in this component at all. List semantics are correct (`<ul>/<li>` used for "Common Issues," not divs styled as a list). No tables are present. No form inputs are present, so label-association is not applicable.

The heading structure is not logical: fixture line 11 (`<h1>Introduction to Web Accessibility</h1>`) is followed directly by fixture line 13 (`<h3>Why Accessibility Matters</h3>`), skipping h2 entirely. The same skip repeats for fixture lines 19, 22, and 29 (`WCAG Guidelines`, `Common Issues`, `Getting Started` — all h3), before an h2 finally appears at fixture line 31 (`Tools and Resources`) and again at fixture line 34 (`Conclusion`). This is independently corroborated by two sources beyond the raw JSX: axe-core's `heading-order` rule (moderate impact, sample selector `h3:nth-child(2)`, help text "Heading levels should only increase by one") and the KAT reading-order census, which recorded the heading level sequence as 1, 3, 3, 3, 3, 2, 2 with no level-2 heading between the level-1 and the four level-3 headings. The digest itself flags that axe's `:nth-child` selector and the census's `:nth-of-type` indexing aren't confirmed to name the identical DOM node without the raw HTML — but the census's own independently-recorded level sequence establishes the skip on its own terms regardless of that cross-tool node-identity question, so the underlying defect is not in doubt even though the single-node cross-reference is.

Also present in the JSX, but not covered by either supplied artifact: `<h3>Getting Started</h3>` (fixture line 29) is followed immediately by `<h2>Tools and Resources</h2>` (fixture line 31) with no paragraph or content between them — "Getting Started" is a heading with no body content under it. Flagged below in Open Questions rather than scored, for reasons explained there.

The component itself renders only an `<article>` — no `<main>`, no `<html>`, no page shell (expected, since this is a component fragment, not a full page). Axe's scan of the rendered page reports `landmark-one-main` (moderate, selector `html`, "Document should have one main landmark") and `region` (moderate, selector `#root`, "All page content should be contained by landmarks"). Taken at face value this means the rendered test page has no `<main>` ancestor anywhere. Whether that's a defect in this component specifically, or an artifact of the isolated single-component test harness the axe scan was run against, is addressed under Realist Check below — it is not something the component's own source code can resolve either way, since a component that is meant to be embedded in a larger page legitimately should not hard-code its own `<main>` (doing so would risk duplicate `<main>` elements if this component is ever rendered more than once on a page, e.g., in a list of posts).

**Phase 3 — ARIA Pattern Compliance Audit.** Not applicable. There are no interactive widgets (no tabs, menus, toggles, disclosure, combobox, or dialog patterns) to check against a WAI-ARIA APG pattern. This is a genuinely clean, not a rubber-stamped, result — corroborated by the KAT census's zero-interactive-role finding, not just by reading the JSX.

**Phase 4 — Focus Management Review.** Not applicable. With no focusable interactive elements, there is no tab order, focus trap, focus restoration, or roving-tabindex behavior to evaluate. The supplied CSS contains no `outline` or `:focus` rules at all, so nothing in this component actively strips or alters default browser focus styling — moot in practice here since nothing in the component is focusable, but worth noting since it means no anti-pattern of the "focus-indicator suppressed" kind exists in the given code.

**Phase 5 — State Communication Audit.** Not applicable. No loading, error, success, disabled, or toggled states exist anywhere in this static component, and no visual-only state indicators (icons, color-only cues, symbol characters) are present. This is corroborated by the census's empty `declared_live_regions`, `declared_broken_aria_refs`, and `declared_alternate_reading_order` fields — there is nothing dynamic here to communicate to assistive technology, so there is nothing missing either.

**Phase 6 — Multi-Perspective Review.** See the Multi-Perspective Notes and Perspective Alarm table below.

**Phase 7 — Gap Analysis.** Checked against the full "missing items" checklist (missing error handling, announcements, keyboard-shortcut docs, reduced-motion, touch targets, `lang` attribute, focus restoration, skip links, `aria-current`, field associations, `aria-describedby`, `aria-controls`, composite-widget roles, list semantics, `visibility:hidden` focus-reveal traps, missing `inert`, exposed pseudo-element content, exposed icon fonts, reverse skip-links, accessible-auth alternatives, dragging alternatives, consistent help, caption/transcript infrastructure, sticky-obscured focus, focus-appearance threshold, redundant entry) — the only items that apply to this component are: the heading-structure gap already identified in Phase 2, the landmark-structure gap already identified in Phase 2, and a missing reverse skip-link opportunity given this is a genuinely long-form, multi-section document (flagged as an Enhancement below, since nothing blocks navigation without it).

Checked against the nine known anti-patterns from the prior third-party audit (broadcast-vs-association misuse, `title`-as-accessible-name, ARIA-without-visible-label, else-branch coverage gaps, single-selector scope gaps, `<td>` row headers, `role="presentation"` on real data tables, verbose alt text on decorative/labeled images, missing DOM-verification on ARIA fixes) — none apply. This component has essentially no ARIA or table surface area to misapply.

Checked against the documented axe/jsx-a11y false-positive patterns (non-interactive-element-interactions, `anchor-is-valid` on framework links, color-contrast-on-gradients, `region`-on-portal-content, `aria-allowed-attr`-via-spread) — none of the three reported axe violations (`heading-order`, `landmark-one-main`, `region`) match a known false-positive shape. They are treated as valid findings, not tooling noise.

## Critical Findings (blocks access)

None. Nothing in this component traps a keyboard user, silently fails a form, or makes core content entirely unreachable for any user group.

## Major Findings (significantly degrades experience)

1. **Repeated heading-level skip produces a misleading document outline.** `<h1>Introduction to Web Accessibility</h1>` (fixture line 11) is followed directly by four consecutive `<h3>` headings (fixture lines 13, 19, 22, 29 — "Why Accessibility Matters," "WCAG Guidelines," "Common Issues," "Getting Started") with no intervening `<h2>`, and the first `<h2>` elements don't appear until fixture lines 31 and 34 ("Tools and Resources," "Conclusion"). A screen reader user building a mental model of this page via a headings list (VoiceOver Rotor > Headings, NVDA Elements List, JAWS Insert+F6 — a primary navigation pattern for long-form content, which this is) would see an outline where "Tools and Resources" and "Conclusion" sit at the same nesting depth as "Introduction to Web Accessibility" itself (both h1 and h2 are one level from the implicit root), while the four h3 sections are the only content actually nested under the h1. That inverts the article's real structure: the two h2 sections read later in the document and clearly continue the same article, yet the heading levels present them as siblings to the introduction rather than as its later subsections.
   - Confidence: MEDIUM. HIGH on the raw fact of the skip (independently confirmed by axe-core's `heading-order` rule and by the KAT census's own recorded level sequence — 1, 3, 3, 3, 3, 2, 2 — which stands on its own regardless of the unresolved question of whether axe's `h3:nth-child(2)` selector and the census's `:nth-of-type` indexing name the identical DOM node). MEDIUM specifically on the "inverted outline" interpretive layer, since that is this reviewer's structural reasoning about how a headings-list view would present the sequence, not something either tool asserts directly.
   - Why this matters: full content is still reachable by linear reading or "next heading at any level" navigation — nothing is hidden. But a user relying on level-filtered heading navigation, or on the headings list to decide what to read next, gets a materially wrong picture of which sections belong under which. That's a real degradation of navigation efficiency and comprehension for a long-form piece, not a cosmetic gap.
   - Fix: either promote the four h3 sections' implied grouping to an explicit h2 (if they are genuinely one topic's subsections and deserve their own umbrella heading), or, if "Why Accessibility Matters," "WCAG Guidelines," "Common Issues," and "Getting Started" are each meant to be top-level sections of equal standing with "Tools and Resources" and "Conclusion," relabel all six as h2. Either fix restores a heading sequence that increases by one level at a time and correctly nests subsections under their parent section.
   - WCAG grounding: 1.3.1 Info and Relationships (AA) — the semantic structure must convey the same relationships a sighted reader infers from the visual hierarchy (font-size 32/24/18px, descending). Note for calibration: axe classifies its own `heading-order` rule as `cat.semantics`/`best-practice`, not a discrete SC failure, and WCAG's own heading-specific criterion, 2.4.10 Section Headings, is AAA — not an AA failure by itself. 1.3.1 is the defensible AA anchor here because the structural mismatch is a relationships-not-conveyed problem, not because "heading-order" maps cleanly to a single AA success criterion.

## Minor Findings (friction but workaround exists)

1. **Content may not be contained in a landmark region (needs verification against the real page shell).** Axe reports `landmark-one-main` (moderate, selector `html`, "Document should have one main landmark") and `region` (moderate, selector `#root`, "All page content should be contained by landmarks") against the rendered test page. Screen reader users who navigate by landmark region (NVDA/JAWS "d", VoiceOver Rotor > Landmarks) would lose a jump-to-main-content shortcut if this holds true in production — though full content remains reachable via heading navigation or linear reading, so this is friction with a workaround, not a block.
   - Confidence: MEDIUM.
   - Why this matters: if genuinely unwrapped by `<main>` in production, landmark-navigating screen reader users lose a common shortcut. If the component is actually mounted inside a page template that already supplies exactly one `<main>`, this finding doesn't apply to real usage at all.
   - Fix: verify the actual hosting route/page template wraps this component's output in a single `<main>` landmark. Do not add `<main>` inside `BlogPost` itself — this component's root is `<article>`, and if `BlogPost` is ever rendered more than once on a page (e.g., in a post list), a `<main>` inside each instance would create duplicate `<main>` landmarks, which is its own defect.
   - Mitigated by: this axe scan measures an isolated single-component test harness page (`heading-hierarchy-skipped.html`), not a confirmed production route. A component whose own markup is just `<article>` (no `<html>`/`<body>`) is exactly the shape expected of something meant to be embedded in a larger page shell that already owns the single `<main>` landmark — the finding is real for the page as scanned, but its applicability to real usage is unconfirmed from source alone.
   - WCAG grounding: 1.3.1 Info and Relationships (AA) — landmark structure is one of the mechanisms by which document relationships are exposed programmatically.

## Enhancements (best practice not met, no access barrier)

- This is a genuinely long-form, multi-section document (six headings across the visible content). No mechanism exists to jump back to a table of contents or to the top after reading a section — a keyboard/screen-reader user who tabs or reads to the end must reverse-navigate through everything to get back. Consider a visually-hidden-until-focused "back to top" or "back to contents" link at section boundaries. No access barrier today since heading navigation and linear reading both still work; this is a navigational-efficiency improvement, adjacent to WCAG 2.4.1 Bypass Blocks in spirit rather than a literal failure of it (2.4.1 is about *skipping* repeated blocks going forward, not reverse navigation — named here as the closest existing citation, not a claimed violation).

## What's Missing

- **A clear, level-consistent information architecture expressed through headings.** The heading levels as written don't match what the visual hierarchy (and, most likely, the actual content relationships) suggest. This is the same underlying gap as the Major finding above, restated as an absence: there is no heading level in this markup that correctly groups "Why Accessibility Matters," "WCAG Guidelines," "Common Issues," and "Getting Started" as a set distinct from "Tools and Resources" and "Conclusion" — whatever that grouping level should be, it doesn't exist in the current markup.
- **Confirmed single-`<main>` ownership at the page level.** Not something this component's source can resolve, but the measured axe result means it's currently an open gap rather than a confirmed pass. See Minor finding above.

## Verdict Justification

One MAJOR finding (heading-order skip producing a misleading outline, corroborated by two independent measured sources) is enough to warrant REVISE rather than ACCEPT or ACCEPT-WITH-RESERVATIONS — this is a real structural defect with a concrete, low-cost fix, not a cosmetic nit. It does not warrant REJECT: nothing blocks access outright, all content remains reachable by linear reading or unfiltered heading navigation, and the fix is a heading-level relabel, not a redesign.

The protocol's own worked example calibrates an isolated heading-hierarchy gap as MINOR when "landmark structure is clear." That precondition doesn't hold here — the same evidence pack that surfaces the heading-order defect also surfaces landmark-one-main/region violations — and the skip pattern itself is repeated four times rather than occurring once, producing an outline that doesn't just have "gaps" but actively misrepresents which sections nest under which. Both of those are the basis for calibrating this finding up to MAJOR rather than defaulting to the protocol's baseline MINOR example. The landmark finding is calibrated down from what axe's "moderate" impact label might suggest in isolation, to MINOR-with-needs-verification, because the evidence measures an isolated single-component test harness page rather than a confirmed production route, and a bare `<article>` component is exactly the shape expected of something meant to be embedded in a page shell that already owns the `<main>` landmark.

Screen reader is the only perspective landing at MEDIUM (not HIGH) alarm; per the protocol, perspectives at MEDIUM or HIGH should be flagged for deep review via `/perspective-audit` — flagging that escalation signal here rather than invoking it, since a single MEDIUM-alarm perspective driven by one already-well-evidenced finding does not obviously need a separate 7-perspective deep-dive on top of what's already been covered above, but the option is available if the team wants a second pass.

Separately, the fixture's own self-reported checklist claims "No headings for visual styling only." That claim is not fully supported by the evidence: the CSS assigns descending, visually distinct styling to h1/h2/h3 (32px blue, 24px blue, 18px gray) in a way that is at minimum circumstantially consistent with the heading levels having been chosen for visual weight rather than content structure, and the actual outcome — a semantic hierarchy that doesn't match the content's real section relationships — is the defect scored above regardless of intent. This self-report shouldn't be taken at face value on the strength of this evidence.

Phases 3 (ARIA pattern), 4 (focus management), and 5 (state communication) are not "no findings" by omission — they are explicitly not applicable, because this component has no interactive elements, a conclusion corroborated by the KAT census's zero-interactive-role result, not just by reading the JSX. Stating that plainly matters here: a clean bill of health on those three phases carries real signal, not silence.

## Open Questions (unscored)

- `<h3>Getting Started</h3>` (fixture line 29) is immediately followed by `<h2>Tools and Resources</h2>` (fixture line 31) with no paragraph or other content between them — "Getting Started" is a heading with no body content under it. This could be a genuine orphaned/incomplete section, or it could be an artifact of this being a trimmed fixture rather than the full article. Neither supplied evidence artifact speaks to this directly (it's a authoring/content-completeness question, not something axe or a reading-order census would flag as a rule violation), and a developer could plausibly explain it with context not present here (e.g., a truncated example). Held here rather than scored, per self-audit: low confidence plus a plausible non-defect explanation.
- Whether axe's `h3:nth-child(2)` selector and the KAT census's `:nth-of-type`-based indexing for the skipped heading refer to the exact same DOM node is not established by either artifact (per the digest's own caveat) — doesn't change the Major finding's substance, since the census's independently-recorded level sequence confirms the skip regardless, but it's an open precision gap in the evidence, not in the underlying defect.
- Whether `BlogPost` is normally rendered inside a page template that already supplies a single `<main>` landmark is unknown from source alone — this determines whether the Minor landmark finding requires any code change to this component at all, or is entirely a page-shell matter.
