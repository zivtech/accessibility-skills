# Accessibility Design Review: Modal Dialog Component

**VERDICT: ACCEPT-WITH-RESERVATIONS**

**Overall Assessment**: This is an unusually complete, defensively-coded implementation of the WAI-ARIA APG Modal Dialog pattern — all seven core requirements (dialog role, `aria-modal`, `aria-labelledby`, focus-into-dialog-on-open, focus trap, Escape-to-close, focus-restore-on-close) are present in source, and three of the most failure-prone ones (focus-trap cycling, Escape-close, focus-restore) are independently confirmed by a supplied driven-keyboard trace, not just code reading. The gaps that remain are not the common "Modal 101" mistakes (no trap, no restore, unlabeled backdrop) — they are more subtle: the component bakes in a single-instance assumption (hardcoded id, unscoped global key listeners) that will break the moment this component is nested or stacked, and a couple of code-completeness gaps (an unreachable CSS rule, an incomplete focusable-element filter) that don't fire in this fixture but are real latent debt in a reusable component.

**Pre-commitment Predictions**: Before reading the code, the standard modal-dialog failure modes were expected: focus trap not implemented or partial, focus not restoring after close, a backdrop that's clickable but unlabeled/still focusable, or close-button semantics built on a div instead of a `<button>`. None of these occurred — the implementation actively defends against the two hardest versions of these problems (a text-selection drag ending on the backdrop, and React's async unmount timing for the initial focus-in). The actual gaps found live one level up: instance-scoping and a couple of incomplete defensive branches. That is itself worth noting — the predictable checklist items are solid; the review had to go looking for what a single-instance smoke test would never surface.

## Investigation Summary (by phase)

**Semantic HTML (Phase 2)**: No ARIA-replacing-native anti-pattern found. The close control is a native `<button>` with `aria-label="Close dialog"` (lines 160–164), not a `div role="button"`. The title is a real `<h2>` (line 159). The overlay wrapper correctly uses `role="presentation"` (line 149) on a div that has no semantic content of its own; per the ARIA spec this does not suppress the explicitly re-asserted `role="dialog"` on its child (line 154), so the dialog itself is still exposed correctly. No table, list, or landmark misuse — none of that markup is present. Clean.

**ARIA pattern compliance (Phase 3)**: Matches the WAI-ARIA APG **Dialog (Modal)** pattern completely at the attribute level: `role="dialog"` + `aria-modal="true"` (lines 154–155), `aria-labelledby="modal-title"` pointing at the actual title heading (line 156 → line 159), focus moved into the dialog on open (lines 44–49), a focus trap (lines 79–123), Escape-to-close (lines 65–76), and focus restored to the invoking control on close (lines 54–58). All seven elements the pattern requires are present — none of the usual "80% implemented" gaps (e.g., `aria-expanded` toggling with no restoration) apply here because there's no toggle state to communicate in the first place.

**Focus management (Phase 4)**: `getFocusableElements` (lines 27–32) is recomputed on every Tab press rather than memoized once at open — this correctly handles content that changes shape while the modal is open. The trap correctly special-cases focus landing outside the dialog (lines 100–104) and correctly special-cases the "click-drag text selection that releases over the backdrop" scenario in the overlay handlers (lines 127–142), which a naive `e.target === e.currentTarget`-only implementation gets wrong. The initial focus-in is deliberately deferred with `setTimeout(fn, 0)` (lines 45–49) to survive paint/portal-mount timing; the focus-*out* restoration (lines 56–57) is **not** similarly deferred — see Open Questions.

**State communication (Phase 5)**: Modal.tsx has no toggling ARIA state to communicate (no `aria-expanded`/`aria-pressed`/`aria-selected` anywhere in this component), so the "state not communicated to AT" failure mode this phase usually targets doesn't apply. The one visual-symbol-as-content case (the "✕" glyph as the close button's only child, line 165) is safe because `aria-label="Close dialog"` on the same element (line 163) overrides the accessible name computation — the supplied trace confirms the announced name is literally `"button, Close dialog"` with no leaked "times"/"multiplication sign," so this does **not** trigger the visual-text-symbol anti-pattern despite superficially matching its shape.

**Gap analysis (Phase 7)**: see "What's Missing" below.

**Multi-perspective + Realist Check + self-audit**: see the dedicated sections below; findings surfaced in earlier phases were down-graded or moved to Open Questions where a developer could reasonably refute them from context this review doesn't have (per Phase 9 rules).

**Critical Findings** (blocks access): None identified. Nothing in source or in the supplied evidence blocks access entirely for any user group in the scenario actually exercised.

**Major Findings** (significantly degrades experience):

1. **Single-instance assumptions are baked into a hardcoded id and unscoped global key listeners — this breaks under nested or stacked modal usage.**
   - Evidence: `id="modal-title"` (line 159) and `aria-labelledby="modal-title"` (line 156) are literal strings, not generated per-instance (no `useId()` or equivalent). The Escape handler (line 74, `document.addEventListener('keydown', handleEscape)`) and the Tab-trap handler (line 121, `document.addEventListener('keydown', handleTabKey)`) are both attached at `document` scope with no "am I the top-most open modal" check and no `stopPropagation()`.
   - User group impacted: Screen reader users (duplicate DOM ids make `aria-labelledby` resolution undefined-behavior — browsers/AT typically resolve to the *first* matching id, so a second, actually-focused dialog can announce the *first* dialog's title) and keyboard-only users (two independently-registered Tab-trap handlers on the same `document` object will both fire on every Tab press once two instances are open, and each computes its own `firstElement`/`lastElement` from its own `modalRef` — the outer dialog's trap can redirect focus into content that is now visually covered by the inner dialog).
   - Expected behavior per WAI-ARIA APG Dialog (Modal) pattern: each dialog instance is independently and unambiguously identifiable and only the top-most open dialog captures Escape/Tab.
   - Fix: generate the title id per-instance (`const titleId = useId()`), and give the key-listeners either a "only run if this instance is the top-most open modal" check (a shared module-level stack/counter of open instances) or route through a single shared listener that dispatches only to the top-most registered instance — this is the standard solved pattern in modal libraries like Radix UI / React Aria.
   - Confidence: MEDIUM. Not reproduced in the supplied evidence — every trace observation (`focus-sequence-full-trace`, steps 0001–0006) shows only one modal instance ever open. This is a source-reasoning finding, not a measured one.
   - **Realist Check (Phase 8)**: (1) Realistic worst case — a "confirm delete" dialog launched from inside this exact "Settings" modal (an extremely common real-world composition for a general-purpose, exported `Modal` component) gets the wrong or ambiguous announced title for screen reader users, and the two dialogs' Tab traps can fight over which content is reachable for keyboard users. (2) User groups: screen reader and keyboard-only. (3) Detection speed: slow — axe-core's `duplicate-id`/`duplicate-id-aria` rules *would* catch this, but only if a scan runs while two instances are simultaneously open, which a single-path smoke test (like the one this fixture's own evidence trace ran) will never trigger; this is the kind of thing that surfaces from a real nested-dialog feature or a user bug report. (4) Proportionality: not inflated — this is a shared, reusable component, and "dialog launched from a dialog" is a common enough composition that I'm not downgrading this to MINOR despite it being unreproduced here.
   - Why kept at MAJOR rather than REJECT/REVISE for the whole component: the fixture's own tested usage (single instance) works correctly and is empirically confirmed. This is a composability landmine, not a live break in what was shipped and tested.

**Minor Findings** (friction but workaround exists):

- **No `inert`/`aria-hidden` fallback on background siblings while the modal is open.** The component relies entirely on `aria-modal="true"` (line 155) to signal to assistive technology that background content should be excluded from non-linear (browse-mode/virtual-cursor) navigation — this is in fact the documented purpose of `aria-modal`, and modern AT/browser pairings generally honor it, so this is not a proven active break. But it is a single point of failure: the JS-level Tab-trap only governs sequential Tab navigation, not a screen reader's own virtual-cursor movement, so any AT/browser combination with incomplete `aria-modal` support would let a screen reader user browse into and interact with inert background content. Fix (defense-in-depth, not required for the primary path): apply the `inert` attribute (or `aria-hidden="true"`) to the modal's background siblings for the duration `isOpen` is true.
- **`getFocusableElements`/`FOCUSABLE_SELECTOR` excludes `display:none` but not `visibility:hidden`.** The filter comment at lines 29–31 states its intent explicitly ("display:none elements produce no client rects... must not become wrap anchors") — but `visibility:hidden` elements still report non-zero client rects, so a `visibility:hidden`-but-not-disabled interactive element inside `{children}` would be included in the tab sequence as an invisible phantom stop. Not reachable via anything in Modal.tsx's own markup (the close button is always visible and enabled), but reachable via consumer-supplied modal-body content that uses `visibility:hidden` rather than `display:none`/`hidden`/`disabled` to hide a control. WCAG 2.4.7 Focus Visible is the relevant anchor (a keyboard user could tab to a target with literally nothing visible, including no focus outline, since the whole element is invisible). Fix: add a `visibility` check (e.g., `getComputedStyle(el).visibility !== 'hidden'`) alongside the existing `getClientRects().length > 0` check.
- **The `.modal-dialog:focus` CSS rule (lines 205–208) is currently unreachable.** The dialog container (`<div ref={modalRef} ... role="dialog">`, lines 151–157) has no `tabIndex`, and no code path ever calls `.focus()` on `modalRef.current` — the zero-focusable-elements branch (lines 88–91) only calls `e.preventDefault()` and returns. This means the APG-sanctioned fallback of focusing the dialog container itself when no better target exists isn't actually wired up, and the visible-focus CSS written for exactly that case can never render. Not a live defect in this fixture — the close button is unconditionally rendered and unconditionally enabled, so `getFocusableElements` can never return an empty array through Modal.tsx's own markup — but it's incomplete defensive code that would matter the moment a consumer can hide/disable everything else inside a modal (e.g., a fully-disabled-during-save state). Fix: add `tabIndex={-1}` to the dialog container and fall back to `modalRef.current.focus()` when `getFocusableElements(...)` returns an empty array, both at open-time and inside the Tab-trap's zero-length branch.

**Enhancements** (best practice not met but no access barrier):

- The supplied driven-trace evidence exercises only forward Tab (steps 0003–0005 cycle close→save→close→save); Shift+Tab wrap-around at the trap's boundaries (lines 106–111) is implemented in source but not exercised by any evidence read for this review. Worth a dedicated Shift+Tab pass (Playwright or another driven session) before treating the trap as fully verified in both directions.
- The close button's hit target was not pixel-measured. From the CSS box model alone (`font-size: 24px`, `padding: 4px 8px`, lines 224–229) it appears comfortably above the 24×24 CSS px minimum (WCAG 2.5.8), but this is an estimate from source, not a rendered measurement.

**What's Missing** (gaps, unhandled edge cases, unstated assumptions):

- No coordination mechanism for two simultaneously-open `Modal` instances (shared literal id, unscoped global listeners) — see Major Finding 1.
- No `inert`/`aria-hidden` applied to background content while open — the component leans entirely on `aria-modal` support rather than adding a redundant, AT/browser-support-independent guarantee.
- No exercised evidence (in what was supplied) for the Shift+Tab direction of the focus trap.
- No live fallback focus target for the zero-focusable-elements case — the container isn't focusable and the CSS written for that case is dead.

**Multi-Perspective Notes**:

- **Screen reader user**: The core pattern is solid and partially *measured*, not just read — the supplied trace's simulated screen-reader announcement at the moment the dialog opens is `"dialog, Settings, modal"` immediately followed by `"button, Close dialog"` (trace step_0002), which confirms the dialog role, the title text resolved through `aria-labelledby`, and the modal signal are all reaching the accessibility layer, and confirms the close button's name is exactly `aria-label`'s value with no leaked glyph. The two real gaps for this perspective are both about composition, not the tested single-instance path: the hardcoded title id (Major Finding 1) and the lack of a redundant inert/aria-hidden guarantee on background content (Minor Finding 1).
- **Keyboard-only user**: Tab/Shift+Tab containment and Escape-to-close are the central interaction model, and the forward-Tab direction is empirically confirmed cycling correctly between the two focusable elements the trace exercised (close ↔ "Save changes", wrapping in the forward direction at trace steps 0003→0004→0005) with focus correctly restoring to the trigger button on Escape (step 0006). The unexercised Shift+Tab direction, the `visibility:hidden` gap in the focusable-element filter, and the dead fallback-focus CSS are all keyboard-relevant but none of them fire against this component's own hardcoded markup today.
- **Low vision user (200% zoom, high contrast)**: The dialog's sizing is relative/viewport-based (`width: 90%`, `max-width: 500px`, `max-height: 80vh`, `overflow-y: auto`, lines 194–202) rather than fixed-pixel, which reflows correctly rather than clipping at zoom. Focus-indicator contrast was hand-verified against the WCAG relative-luminance formula rather than eyeballed: `#0066cc` outline against the white dialog background computes to roughly **5.6:1** (well past the 3:1 non-text minimum for 2.4.11/2.4.13), and the close icon's `#666` (default) / `#333` (hover) against white compute to roughly **5.7:1** and well over **12:1** respectively (both past the 4.5:1 text minimum). No contrast problem found in Modal.tsx's own styles. Worth flagging transparently: the supplied trace shows an inconsistent focus-indicator *area* pass/fail result across repeat visits to two other on-page buttons ("Open settings," "Save changes") whose CSS was not part of this review — but the *one* element whose focus CSS **was** reviewed here (the close button, `.modal-close:focus`) shows a **stable, passing** area/AAA result across both of its visits in the trace (steps 0002 and 0004). That pattern points away from Modal.tsx's own styling as the cause of the inconsistency; see Open Questions.
- **Cognitive accessibility**: Modal.tsx's own chrome offers three independent, low-effort ways to dismiss (Escape, the labeled Close button, or a backdrop click that correctly ignores accidental text-selection drags per the comment and logic at lines 132–141) with no destructive default action. The actual modal-body content (a "Save changes" control, per the trace) is consumer-supplied via `{children}` and outside what this component's own source shows — any redundant-entry or confirm-before-destructive-action concerns belong to that content, not to this review.

### Perspective Alarm Levels

| Perspective | Alarm Level | Trigger Signal |
|-------------|-------------|-----------------|
| Screen reader | HIGH | Custom dialog with hand-rolled title association and reliance on `aria-modal` for background inertness; hardcoded id risks under composition |
| Keyboard-only | HIGH | Custom focus-trap is the entire interaction model; two unexercised/incomplete defensive branches (Shift+Tab evidence, zero-focusable fallback) |
| Low vision | MEDIUM | Standard reflow-friendly sizing; focus-indicator contrast independently verified by calculation |
| Cognitive | LOW | No multi-step logic, timeouts, or destructive-action flow visible in Modal.tsx itself; body content is opaque to this review |
| Vestibular & motion | LOW | Only a 0.2s color hover transition; no parallax or auto-playing content |
| Auditory access | LOW | No media elements present |
| Environmental contrast | MEDIUM | Blue focus ring and icon colors checked against the WCAG contrast formula; all computed values clear their thresholds |

Screen reader and Keyboard-only both land at HIGH — per the escalation rule, this component is a reasonable candidate for a deeper `/perspective-audit` pass, particularly focused on the composition/instance-scoping questions this review could only reason about from source rather than measure.

**Verdict Justification**: The component earns ACCEPT-WITH-RESERVATIONS rather than a clean ACCEPT because of one MAJOR, evidence-unreproduced-but-architecturally-real finding (single-instance assumptions in the title id and the global key listeners), and rather than REVISE/REJECT because that finding does not affect the tested, single-instance usage this fixture actually demonstrates — which is empirically confirmed working across focus-trap cycling, Escape-close, and focus-restore. The Minor findings (missing inert/aria-hidden redundancy, the `visibility:hidden` filter gap, the dead fallback-focus CSS) are real but none of them are reachable through this component's own hardcoded markup today; they are technical debt to close before this component is reused in a context that would expose them. Nothing here was inflated by review momentum — the predictable "Modal 101" failure modes this review expected going in were checked for specifically and none were found, which is itself the reason the review had to look one level deeper to find anything worth flagging at all. Recalibration performed: the single-instance finding was seriously considered as CRITICAL (given it can cause "wrong dialog title" and "competing focus traps" for screen reader and keyboard users) but was held at MAJOR rather than CRITICAL because CRITICAL is reserved for defects that block access *in the scenario actually shipped and tested*, and nested/stacked usage is not that scenario here.

**Open Questions (unscored)**:

- The Escape (line 74) and Tab-trap (line 121) listeners are `document`-level, bubble-phase, with no `stopPropagation()`. If a future consumer places a nested interactive widget with its own Escape handling (a combobox, a date picker) inside `{children}`, pressing Escape to dismiss just that inner widget could also cascade up and close the whole modal. Not reproduced — the only modal-body content shown in evidence is a single button — and a developer could reasonably refute this as out of scope for the component as currently used. Moved here rather than scored.
- The focus-restore call on close (line 57) is not deferred with `setTimeout`, while the focus-in call on open (lines 45–49) deliberately is. This is very likely safe, since the restoration target (the original trigger element) is not part of the subtree React unmounts when the modal closes — but I can't fully rule out a scenario where a parent's `onClose` handler also removes or re-renders the trigger element itself in the same update. Low confidence; flagged rather than scored.
- The `<h2 id="modal-title">` heading level (line 159) is correct in isolation and matches the "Accessibility Features Implemented" claim, but this review has no visibility into the invoking page's own heading hierarchy, so whether h2 is the *right* level in every context this component is dropped into can't be confirmed either way from what was supplied.
- The inconsistent focus-indicator area/AAA pass-fail result for the two non-Modal.tsx buttons in the supplied trace (`"Open settings"` at steps 0001/0006, `"Save changes"` at steps 0003/0005) is real and worth someone's attention, but its cause can't be attributed from what this review was given — the CSS for those two elements was never supplied, they sit outside Modal.tsx, and the one element whose CSS *was* reviewed here showed stable results across repeat visits. Most likely a harness-page styling detail or a measurement-timing artifact rather than a Modal.tsx defect; noted for transparency rather than scored against this component.
