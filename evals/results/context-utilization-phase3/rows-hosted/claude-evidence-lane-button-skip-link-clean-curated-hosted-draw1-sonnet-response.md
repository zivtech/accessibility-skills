**VERDICT: ACCEPT-WITH-RESERVATIONS**

**Overall Assessment**: This is a clean, well-structured layout component — correct landmarks (`nav`/`main`/`footer`), correct list semantics for navigation, no ARIA masking bad HTML, and a skip-link reveal technique (`position: absolute; top: -40px` → `top: 0` on focus, not `visibility:hidden`/`display:none`) that correctly avoids the classic keyboard catch-22. But the fixture's own stated requirement — "Clicking skip link focuses main content" — is not backed by a focusable target: `<main id="main-content">` carries no `tabindex`, and a plain `<main>` element cannot receive script or fragment-navigation focus without one. The component's self-reported checklist ("✓ Skip link functional") conflates "href points at the right id" with "moves focus," and those are not the same claim. That gap, plus one measured axe-core finding and one routine wayfinding gap, are enough to withhold a clean ACCEPT, but nothing here requires architectural rework.

**Pre-commitment Predictions**: Before reading the code, the predicted top candidates for a skip-link/nav layout component were: (1) skip-link target not actually focusable (the single most common skip-link defect); (2) missing or incorrect focus indicator on the skip link itself; (3) missing `aria-current` for the active nav item; (4) heading-hierarchy gaps; (5) landmark structure missing or mis-nested. Prediction (1) was confirmed directly in source. Prediction (3) was confirmed. Prediction (5) was *not* confirmed — landmark structure is fully correct, which the review states plainly rather than manufacturing a finding to fill a predicted slot. Prediction (4) was confirmed only at the rendered-page level via measured axe evidence, with an important caveat about whose responsibility it is (see Minor Findings). Prediction (2) surfaced as a genuine open question rather than a scored finding, because the given CSS doesn't rule it out but doesn't confirm it either.

**Critical Findings** (blocks access):

None. Nothing in this component locks a user category out entirely — the layout remains navigable by continued Tab presses even where the skip mechanism underperforms.

**Major Findings** (significantly degrades experience):

1. **Skip-link target is not a valid focus target — `tabindex="-1"` is missing on `#main-content`.** See fixture Component Code, line 25: `<main id="main-content">`. Per the HTML focus model, an element must either be intrinsically focusable (form controls, links with `href`, etc.) or carry a `tabindex` attribute to become a valid focus target for `.focus()` or fragment navigation. A bare `<main>` has neither. Activating the skip link (fixture Component Code, lines 12–14: `<a href="#main-content" className="skip-link">Skip to main content</a>`) will scroll the viewport to `<main>` and update the URL fragment/`:target` state, but will not move document focus there — focus effectively resets to `<body>`, so the very next Tab press restarts sequential navigation from the top of the document (back through the skip link and all four nav links) rather than landing inside main content. This directly contradicts the fixture's own stated requirement under "Expected Behavior": "Clicking skip link focuses main content."
   - User group impacted: keyboard-only users and screen reader users — precisely the audience the skip link exists to serve. Screen reader users get no landmark/heading announcement on activation (because nothing new receives focus), so activating "Skip to main content" produces no perceptible confirmation that anything happened.
   - WCAG: 2.4.1 Bypass Blocks (Level A) — the mechanism to bypass repeated blocks must actually deliver the user past them, not just visually scroll past them. Supporting: 2.1.1 Keyboard (Level A), since the entire mechanism is keyboard-mediated.
   - Confidence: HIGH on the code fact (the `tabindex` attribute is absent from the source shown — directly observable, not inferred) and on the general behavior (this is stable, long-documented HTML/browser focus-model behavior, not version-specific speculation). MEDIUM on the live-browser consequence for this exact fixture, because no keyboard-driven trace exists to confirm it (see evidence discussion below) — this finding is static-code-and-platform-behavior reasoning, not a measured keyboard-a11y-tester/Playwright/agent-browser result.
   - Could the developer refute this with context not shown? Possibly, if a JS handler elsewhere calls `main.focus()` manually after the scroll — but no such handler appears anywhere in the given component, and the fixture is presented as the complete implementation under review.
   - Fix: add `tabindex="-1"` to `<main id="main-content">`. Optionally reinforce with an `onClick` handler on the skip link that calls `preventDefault()`, scrolls, and calls `.focus({ preventScroll: true })` on the target — this also hedges against older Safari/VoiceOver fragment-focus quirks that have historically been less reliable than Chrome/Firefox even with `tabindex="-1"` present. Verify the fix with a driven keyboard test (agent-browser, Playwright, or keyboard-a11y-tester) rather than static review alone, since this exact defect class is what automated DOM-shape scanners (axe-core) cannot detect — confirmed by the evidence pack, which contains zero interaction-defect artifacts for this fixture (see "What's Missing").

**Minor Findings** (friction but workaround exists):

1. **Measured axe-core finding: `page-has-heading-one`, impact "moderate," on the rendered fixture page** — evidence: `evals/results/context-utilization-phase3/raw/axe-batch-2026-08-25/004-127-0-0-1-8777-button-skip-link-clean-html.json`, `.viewports["1280x800"].violations[0]`: `{"id":"page-has-heading-one","impact":"moderate","tags":["cat.semantics","best-practice"],"node_count":1,"sample_selectors":["html"]}`, from a single-page scan of `http://127.0.0.1:8777/button-skip-link-clean.html` (27 passes, 62 inapplicable, 0 incomplete). This is real, measured evidence, not estimated. I am rating it MINOR rather than MAJOR after applying the Realist Check, for three converging reasons stated explicitly rather than asserted: (a) axe itself tags this rule `best-practice`, not a numbered WCAG success criterion — there is no direct SC that requires "at least one `<h1>`" the way there is for, say, missing form labels, so I am not going to force-fit a precise WCAG citation the tooling itself doesn't assert; (b) `MainLayout` is a content-agnostic wrapper — it renders whatever `children` supplies inside `<main>` and does not itself own page content, so the absent-h1 may be a property of what was rendered into the slot during this scan, not a defect in the layout component under primary review; (c) landmark-based navigation (`nav`, `main`, `footer`) remains fully intact as an alternative screen-reader wayfinding path even without a top-level heading, which is a genuine (not thin) workaround. Closest WCAG reference points if a citation is wanted: 1.3.1 Info and Relationships / 2.4.6 Headings and Labels (Level AA) — offered as the nearest relevant principle, not as a precise match, since neither SC literally mandates exactly one `<h1>` per page.
   - User group: screen reader users navigating by heading (H key) get no page-level orientation cue on arrival.
   - Fix: if `MainLayout` is meant to guarantee page structure, consider a required `pageTitle`/`heading` prop that renders the `<h1>` inside `main` (or documents the contract that every page-level component must supply exactly one `<h1>` within `children`). This is a design-hardening recommendation, not a mandate to change this specific fixture.

2. **No `aria-current` mechanism on the active navigation link.** See fixture Component Code, lines 18–21 (`<li><a href="/">Home</a></li>` etc.) and CSS lines 76–86 (`.main-nav a`, `.main-nav a:focus`) — there is no styling or markup hook for a "current page" state at all, visual or programmatic. Since this component appears designed to wrap every page (the fixture is named "Navigation with Skip Link" / `MainLayout`), the same four links render identically regardless of which page is active, with no way — visual or via assistive technology — to tell which one represents the current location. This is a true finding, but calibrated to MINOR per the protocol's own worked guidance ("Missing aria-current on navigation item... True but MINOR. Shouldn't block review unless many such gaps exist") — one instance, no other current-state gaps found alongside it.
   - WCAG: 4.1.2 Name, Role, Value (if `aria-current` is added, the value must be `"page"`, not `"true"`).
   - Fix: pass the active route into `MainLayout` (or read it from a router context) and set `aria-current="page"` on the matching link, paired with a non-color visual indicator (the current CSS only styles `:focus`, not an active/current state).

- **No documented contract for page-level heading ownership.** `MainLayout` neither renders nor requires an `<h1>` from its `children`, and nothing enforces that every consuming page supplies one. The axe finding above is the visible symptom of this absent contract on at least one rendered page.
- **No visible focus-style rule for the skip link itself**, distinct from the well-defined 3px outline given to nav links (see Open Questions — this is not scored as a finding because it can't be confirmed as a real gap from the code shown).

**Verdict Justification**: No CRITICAL findings exist, and the one MAJOR finding is a targeted, well-understood, one-attribute-plus-verification fix rather than an architectural problem — the surrounding design (landmarks, list semantics, the position-based focus-preserving reveal technique, absence of any ARIA-masking-bad-HTML pattern) is sound and doesn't need to go back to `a11y-planner` for redesign. That combination — real, evidence-grounded gap, but no need for rework — is what ACCEPT-WITH-RESERVATIONS is for, rather than REVISE. I checked this component against the nine known anti-patterns from the prior third-party audit (broadcast-vs-association, `title`-as-name, ARIA-without-visible-label, else-branch coverage, single-selector scope, `td`-in-loop row headers, `role="presentation"` misuse, verbose decorative `alt`, missing DOM-verification) and none apply — there's no loop-based markup, no forms, no tables, no images here for most of those checks to bite on. **Open Questions (unscored)**:
- Does the skip link have an intentional focus style of its own? The given CSS defines `.skip-link:focus { top: 0; }` (positional reveal only) but no explicit `outline` rule, and does not set `outline: none` either — meaning the browser's default focus ring should still render unless a global stylesheet not shown here strips it. Moved here rather than scored as a finding because the developer could readily refute it with a global CSS reset this fixture doesn't include, and I have no evidence either way.
- Is this layout used inside a single-page app with client-side routing, or is it a traditional multi-page app? The nav uses plain `<a href="/...">` elements rather than a router `Link` component. From an accessibility standpoint this is neutral-to-positive (it sidesteps the entire "SPA route change doesn't reset focus" problem class by relying on native full-page navigation), but I can't confirm from the given code whether a router elsewhere intercepts these anchors, which would reintroduce that problem class if so.
- Does `MainLayout` render on every page in this application, or only some? This affects how much weight the missing `aria-current` and missing-h1-contract findings should carry — both matter more if this wrapper is truly universal.
