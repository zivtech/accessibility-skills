# Accessibility Design Critic — Review: `MainLayout` (Navigation with Skip Link)

**VERDICT: REVISE**

**Overall Assessment**: This is a small, largely well-built layout shell — semantic HTML choices are correct throughout (real `<a>` elements, real `<nav>`/`<main>`/`<footer>` landmarks, real `<ul>/<li>` list structure, no ARIA masking bad markup), and several common anti-patterns named in this protocol are correctly *avoided* (the skip link uses position-offset reveal rather than `visibility:hidden`, there's no pseudo-element content posing as real content, no font-size is force-pinned). But the component's one marquee feature — the skip link — has the classic, well-documented failure mode of pointing at a fragment target (`#main-content`) that is not itself focusable, which defeats the point of "skipping" for keyboard-only users. A second, independently-verifiable gap is that the nav's only focus indicator falls below the WCAG 3:1 contrast threshold against its own background. Neither finding is measured by the one evidence artifact available (an axe-core scan, which structurally cannot test either of these); both are grounded in direct inspection of the given source and are flagged as design-reasoning findings, not measured facts, per Phase 0 below.

**Evidence Consumed (Phase 0)**: One evidence artifact was provided: an axe-core 4.13.0 scan of `http://127.0.0.1:8777/button-skip-link-clean.html` (`evals/results/context-utilization-phase3/raw/axe-batch-2026-08-25/004-127-0-0-1-8777-button-skip-link-clean-html.json`, viewport 1280×800, http_status 200). It reports exactly one violation — `page-has-heading-one` (impact: moderate, tags `cat.semantics`/`best-practice`, no WCAG SC number stated on the record itself, `node_count: 1`, `sample_selectors: ["html"]`) — plus `incomplete: []`, `passes_count: 27`, `inapplicable_count: 62`. No `heading-order` violation and no other violations exist in the array. **No keyboard-operability, focus-trace, or announcement evidence exists in this pack** (no Playwright, `agent-browser`, `keyboard-a11y-tester`, or `virtual-screen-reader` artifact was supplied). That is an absence of evidence for that interaction class, not evidence that the interactions are fine — axe-core cannot exercise runtime focus movement or fragment-navigation behavior, so a clean axe pass here says nothing about whether the skip link actually moves keyboard focus. This distinction drives the calibration of Major Finding #1 below. axe's ruleset also does not evaluate `:focus`-state outline contrast, so the absence of a `color-contrast` violation neither confirms nor contradicts Major Finding #2 — that finding is my own arithmetic from the literal hex values in the given CSS, not a tool measurement, and I flag it accordingly rather than dressing it up as measured evidence.

**Pre-commitment Predictions**: Before the phase-by-phase read, the predicted issues for a skip-link + static-nav layout shell were: (1) skip-link target not programmatically focusable, (2) skip-link reveal implemented via `visibility:hidden`/`display:none` (the disqualifying anti-pattern) rather than position offset, (3) missing page heading structure, (4) nav/footer text contrast shortfalls, (5) nav focus-indicator contrast, (6) duplicate/misnested landmarks, (7) undersized touch targets, (8) `aria-current` on the active nav item, (9) ARIA masking native semantics. Actual investigation confirmed (1) and (5) as real, evidence-backed findings; confirmed (3) as a real *measured* fact on the tested artifact but with a genuine attribution question (does it belong to this component or to its `children`); and ruled out (2), (4), (6), (7), (9) — the component actively does the right thing on each of those. (8) is real but is explicitly the ENHANCEMENT-tier example in this protocol's own severity scale, so it lands there. No surprises outside these predictions; nothing else emerged in Phases 2–7 beyond what was anticipated for this component type.

**Critical Findings** (blocks access): None identified. Nothing in this component traps keyboard focus, hides core functionality entirely from assistive technology, or causes silent, unrecoverable failure. Said plainly per the calibration rules here: this component does not warrant a CRITICAL rating.

---

**Major Findings** (significantly degrades experience):

1. **Skip-link target is not programmatically focusable, so activating the skip link is unlikely to actually move keyboard focus past the navigation.**
   `<a href="#main-content" className="skip-link">` (Component Code, line 12) targets `<main id="main-content">` (Component Code, line 25), which carries no `tabindex` attribute. Per standard browser fragment-navigation behavior, activating an in-page `href="#id"` link scrolls the target into view, but does **not** synthetically make a non-focusable element receive keyboard focus — focus typically remains on the already-activated link or falls back to the document, not the target. The practical result: a keyboard-only user activates "Skip to main content," the viewport visually jumps to the main region, but the *next* Tab press resumes from wherever focus actually landed — which, absent an explicit fix, is very likely back at the top of the tab sequence (the skip link itself or the first nav item) rather than inside `<main>`. That reintroduces exactly the repeated-navigation burden the skip link exists to eliminate (WCAG 2.4.1 Bypass Blocks), and does so silently — visually it *looks* like it worked because the page scrolled.
   - Confidence: **HIGH** on the code pattern and on the general browser behavior (this is the standard, widely-documented reason the `tabindex="-1"`-on-skip-target fix exists — see WCAG technique guidance for skip links). **Explicitly not measured**: no keyboard-operability trace (Playwright / `agent-browser` / `keyboard-a11y-tester`) exists in the evidence pack to confirm this specific runtime's behavior, per Phase 0. This is a design-reasoning finding, clearly labeled as such, not a captured fact.
   - Why this matters: Keyboard-only sighted users lose the entire benefit of the skip link — they must tab through all four nav items anyway on every page load, which is the specific harm WCAG 2.4.1 exists to prevent. Screen reader users have a partial escape hatch (landmark/region navigation, e.g., NVDA/JAWS "D" or VoiceOver's rotor, works independent of this bug), which is why this is rated MAJOR rather than CRITICAL — access to main content is not blocked, only the shortcut mechanism is defeated. Mitigated by: main content remains reachable by continuing to Tab, and AT users retain landmark navigation as an independent path.
   - Fix: Add `tabindex="-1"` to `<main id="main-content">` so it becomes a valid programmatic focus target, and, for cross-browser certainty, add an `onClick` handler on the skip link (or a `hashchange` listener) that explicitly calls `mainRef.current.focus()` after the native jump. Then verify with an actual keyboard-operability check — Playwright (`page.keyboard.press('Tab')`... `press('Enter')` then assert `document.activeElement`), `agent-browser` snapshot+press, or `keyboard-a11y-tester` — since that evidence does not currently exist for this component.

2. **The nav link focus indicator's contrast against its own background falls below the WCAG 3:1 minimum, and it is the only focus indicator provided.**
   `.main-nav a:focus { outline: 3px solid #0066cc; outline-offset: -3px; }` (CSS, lines 83–86) draws its outline inward (negative offset), meaning the ring sits on top of the link's own background, which is inherited from `.main-nav { background: #333; }` (CSS, line 64) since `.main-nav a` sets no background of its own. Computing WCAG relative luminance directly from these hex values: L(#0066cc) ≈ 0.1386, L(#333333) ≈ 0.0331, giving a contrast ratio of **(0.1386+0.05)/(0.0331+0.05) ≈ 2.27:1**. That is below the 3:1 minimum WCAG 2.2 sets for focus-indicator contrast (2.4.13 Focus Appearance; also the general non-text/UI-component contrast principle behind 2.4.7 Focus Visible). No secondary focus cue exists on these links — no background-color change, no underline, no text-weight change — so this outline is the *sole* signal a keyboard user gets for "this is the currently focused nav item," and it is measurably under threshold.
   - Confidence: **HIGH** — this is a deterministic sRGB→relative-luminance calculation from the exact values in the given stylesheet, reproducible by anyone with the same two hex codes. It is *not* axe-tool-measured (axe's `color-contrast` rule does not evaluate `:focus`-state outline contrast, and indeed the one axe artifact available reports no contrast violation at all — that silence is expected and doesn't corroborate or contradict this finding). If a contrast tool (AccessLint MCP, or a browser DevTools contrast check against the live rendered `:focus` state) is available, use it to corroborate — I'm flagging this as a from-source-values computation, one tier below a tool measurement, not as equivalent to one.
   - Why this matters: Low-vision keyboard users (and anyone in bright ambient light, or on certain display calibrations) will have a harder time perceptually confirming which nav item currently has focus. The outline is not invisible — 2.27:1 is a real, if under-threshold, color difference — so this does not block navigation entirely, but it is a genuine, numeric WCAG shortfall on the only cue provided.
   - Fix: Either lighten the outline color (e.g., a lighter blue or white/`#fff` outline reads far higher against `#333`), thicken/duplicate the indicator with a second high-contrast layer (e.g., add an inset `box-shadow` in a contrasting color alongside the outline), or move the outline outward with a positive offset onto the page background instead of the dark nav background, and re-verify the resulting ratio ≥ 3:1.

**Minor Findings** (friction but workaround exists):

- **Composed test page has no top-level heading (`<h1>`).** axe reports `page-has-heading-one` (moderate) against `http://127.0.0.1:8777/button-skip-link-clean.html`. This is real, measured evidence — but attribution to `MainLayout` itself is genuinely ambiguous: `MainLayout` renders `{children}` inside `<main>` (Component Code, line 26) without prescribing or enforcing any heading, so whether the missing `<h1>` is a defect *in this component* or *in whatever content was passed as `children` for this test render* cannot be determined from the given files. axe's own tags for this rule are `cat.semantics`/`best-practice` with no WCAG SC number attached in the artifact, so I'm not stretching this into a hard numbered-criterion failure — it sits closest in spirit to 1.3.1 (Info and Relationships) / 2.4.6 (Headings and Labels) as a structural best practice, not a clear violation of either. See Open Questions for the ownership question.
- **Skip link has no author-defined `:focus` style of its own.** `.skip-link:focus` (CSS, lines 53–55) only changes `top`; no `outline`, `border`, or other explicit focus treatment is declared for the link itself, so it relies entirely on the browser's default focus ring rendered against a `#0066cc` background (CSS line 46). Some default focus-ring colors are themselves blue-toned, which could produce a low-contrast pairing similar to Major Finding #2 — but this can't be confirmed without seeing the rendered default outline color, and the position-based reveal (the link only appears on screen when focused at all) already provides a strong, non-color location cue that offsets some of the risk. Flagged as Minor/Needs-verification rather than Major because the mitigating location-based signal is present and no `outline: none` or similar suppression exists in the given CSS.

**Enhancements** (best practice not met):

- No nav link carries `aria-current="page"` for the active route (Component Code, lines 18–21). This is explicitly the ENHANCEMENT-tier example in this protocol's own severity scale ("Missing aria-current on current page in nav") — doesn't block access, aids orientation. WCAG 4.1.2 context.
- No explicit `transition` is defined for the skip link's `top` change (CSS lines 42–55), so the reveal is an instant cut rather than an animated slide. This is not a defect — the absence of motion means there's nothing for `prefers-reduced-motion` to need to suppress — but if a future revision adds a slide-in animation for polish, it would need a `prefers-reduced-motion` fallback at that point.

**What's Missing** (gaps, unhandled edge cases, unstated assumptions):

- No defensive `.focus()` call backing up the skip-link's fragment jump (see Major Finding #1's fix) — the current implementation depends entirely on native anchor-fragment behavior with no script-level fallback.
- No keyboard-operability evidence exists anywhere in the supplied evidence pack for this component's single interactive affordance of consequence (the skip link). This is a gap in the *evidence available to this review*, not just a gap in the component, and it's the reason Major Finding #1 is presented as reasoning rather than as a measured fact.
- No stated ownership boundary for page-level heading structure between `MainLayout` (the shell) and its `children` (the page content) — see the Minor finding above and the corresponding Open Question.
- Nothing indicates whether this layout is ever mounted inside a client-side router that intercepts anchor clicks (`preventDefault` + `history.pushState`). If it is, the native fragment-jump behavior discussed in Major Finding #1 could be altered by that router's own handling — nothing in the given files confirms or rules this out.

Keyboard-only sits at HIGH — per this protocol, that should be escalated to `/perspective-audit` for deeper review before this component is considered settled.

**Multi-Perspective Notes**:

- **Screen reader user**: Landmark structure (`nav`, `main`, `footer`) is correct and will surface properly in a landmark rotor; `<footer>` correctly retains its `contentinfo` role since it isn't nested inside a sectioning element. The nav's `aria-label="Main navigation"` is good practice (not strictly required with only one nav present, but harmless and helpful if more landmarks are added later). The 4-item `<ul>` gives a countable list. Two open items: (1) if the skip link's focus doesn't land inside `<main>` (Major Finding #1), a screen reader user's behavior depends on how their AT/browser pairing handles the scroll-without-focus-move case — inconsistent across combinations, which is exactly why the standard fix exists; (2) whatever page was under axe test had no `<h1>` to anchor heading-based navigation, though ownership of that gap is unclear (see Open Questions).
- **Keyboard-only user**: Tab order is logical (skip link → 4 nav links → main content → footer, footer has no focusable elements so it's correctly absent from the sequence). Enter activates links as expected; Space correctly does nothing on anchors (native behavior, not a bug). No modals, no traps. The two Major findings both land squarely on this perspective: the skip link very likely doesn't actually skip anything for a keyboard user in practice, and the one focus indicator that exists is under the numeric contrast bar.
- **Low vision user (200% zoom, high contrast)**: Flexbox column layout and a `max-width` + `margin: 0 auto` main region give no reason to expect forced horizontal scroll at zoom, though this can't be independently confirmed without a live render. No `position: sticky`/`fixed` elements exist in the given CSS, so no WCAG 2.4.11 focus-obscuring risk is evident. Text sizes are never pinned in the given rules (no `font-size` declared anywhere), which favors user/browser resizing. All checked text/background contrast pairs pass comfortably (white/`#333` ≈12.6:1, `#666`/`#f5f5f5` ≈5.27:1, white/`#0066cc` ≈5.57:1); the one contrast shortfall is the focus-outline case in Major Finding #2, which persists at any zoom level since it's a color relationship, not a size one. Nav-link click targets (16px padding on all sides, `display:block`) are comfortably above the WCAG 2.5.8 24×24px minimum under any reasonable font-size assumption.
- **Cognitive accessibility**: No forms, errors, confirmations, or timeouts exist in this component, so most of this lens doesn't apply. Link labels ("Home," "About," "Services," "Contact") are short, plain, and self-explanatory. Given the component's role as a shared layout shell (implied by its name and `children` prop), nav and footer placement should be structurally consistent across every page that mounts it — a real strength, though inferred from the component's evident purpose rather than observed across multiple pages.

---

**Verdict Justification**: REVISE, not REJECT or ACCEPT-WITH-RESERVATIONS. Nothing here blocks access outright (no CRITICAL), and the bulk of the component — semantics, landmarks, list structure, avoidance of the `visibility:hidden` skip-link anti-pattern, text contrast, target sizing — is done correctly and is acknowledged as such rather than nitpicked. But two MAJOR findings survive the Realist Check (Phase 8) with real user-impact reasoning behind them, and one of them (the skip-link focus target) directly undermines the specific, named purpose of this component's one interactive feature — the code's own comment says "Skip link allows keyboard users to bypass navigation," and as written it likely does not reliably do that. That is a concrete, fixable defect (one attribute plus an optional focus-handler), not a stylistic reservation, so REVISE — not a softer verdict — matches the lifecycle guidance to redesign/fix before this ships with confidence. To reach ACCEPT-WITH-RESERVATIONS or better: (1) add `tabindex="-1"` to the `<main>` target (ideally paired with an explicit `.focus()` call) and confirm with an actual keyboard-operability trace, since none currently exists; (2) raise the nav focus-outline contrast to ≥3:1 against `#333`; (3) resolve whether the missing top-level heading is this component's responsibility or its content's. This review did not escalate to a deeper sub-investigation beyond what's captured here, but the HIGH keyboard-only alarm level above is a direct escalation signal for `/perspective-audit`.

**Open Questions (unscored)**:

- Is there a script elsewhere (not included in the reviewed files) that manually manages focus on skip-link activation — e.g., a `hashchange` listener calling `.focus()` on the target? If so, Major Finding #1 may already be mitigated in the real application; nothing in the given files confirms or rules this out.
- Is the missing `<h1>` on the tested page `MainLayout`'s responsibility, or does it belong to whatever content is passed as `children`? If `MainLayout` is intentionally a content-agnostic shell, this may not be a defect in the reviewed component at all.
- Does a global/base stylesheet not included here override the browser default focus ring on `.skip-link`, or add transitions that would need a `prefers-reduced-motion` fallback?
- Is `MainLayout` ever rendered inside a client-side router that intercepts anchor clicks? That could change the fragment-navigation behavior underlying Major Finding #1.
- What does an actual keyboard-operability trace (Playwright, `agent-browser`, or `keyboard-a11y-tester`) show for the skip link's focus movement? This is the single highest-value next artifact to close the evidentiary gap identified in Phase 0 and to move Major Finding #1 from design-reasoning to measured fact.
