**VERDICT: REVISE**

**Overall Assessment**: `BlogPost` uses correct semantic elements throughout (native `h1`–`h3`, a real `<ul>/<li>` list, no ARIA-faked structure) and has no interactive widgets, so most of the 8-phase protocol's ARIA/focus/state phases are genuinely not applicable. The component fails on the one thing it explicitly claims to do well: its heading levels skip from `h1` straight to `h3` four times in a row, then jump back up to `h2` — a measured, dual-source-confirmed structural defect that misrepresents the document outline for both heading-navigating screen reader users and sighted users scanning the page. A second, independently-confirmed gap (an `h3` with no body content before the next heading) directly contradicts the fixture's own claimed accessibility feature.

**Evidence Reviewed** (Phase 0): Two artifacts in the pack are in scope for this component — the axe-core scan of `heading-hierarchy-skipped.html` (`evals/results/context-utilization-phase3/raw/axe-batch-2026-08-25/013-127-0-0-1-8777-heading-hierarchy-skipped-html.json`) and the keyboard-a11y-tester screen-reader reading-order census for the same URL (`evals/results/context-utilization-phase3/raw/heading-hierarchy-skipped-kat-census/sr-census.json`). Both are treated as measured fact per Phase 0. The remaining seventeen axe scans in the pack (`accordion-no-region-role`, `app-focus-order-illogical`, `async-form-vague-success`, `breadcrumb-navigation-no-nav-landmark`, `button-skip-link-clean`, `checkbox-group-no-fieldset`, `combobox-autocomplete-no-listbox-role`, `dashboard-heading-inconsistency`, `data-table-missing-scope`, `expandable-section-no-button`, `file-input-no-labels`, `form-field-vs-summary-errors`, `form-validation-missing-aria-describedby`, `image-carousel-no-region`, `infinite-scroll-no-announcement`, `interactive-dropdown-clean`, `interactive-dropdown-focus-bug`) are explicitly labeled in the pack as sibling pages from the same batch run. None of their violations (form labels, comboboxes, carousels, accordions, tabindex, checkboxes, breadcrumbs) correspond to anything in `BlogPost`'s markup — it contains no form elements, no interactive widgets, and no navigation component — so they are excluded from this review as out of scope rather than cited against this component.

**Pre-commitment Predictions**: For a static long-form content component, the predicted issues were: (1) heading hierarchy skips (very common in blog/CMS-authored content — confirmed, and it is literally the dominant defect), (2) missing landmark/table-of-contents aids for multi-section reading (confirmed, at lower severity, with a scope caveat), (3) content-less or orphaned sections from authoring gaps (confirmed — the "Getting Started" heading, a non-obvious catch that only surfaced from cross-referencing the SR census against the source), and (4) no ARIA/focus/state findings, since the component has no interactive elements (confirmed — Phases 3, 4, and 5 below are reported as not applicable rather than padded with manufactured findings).

**Critical Findings** (blocks access):

None identified. Nothing in this component traps a keyboard user, silently fails validation, or removes content from the accessibility tree entirely. All content remains linearly reachable regardless of the heading-level defect below.

**Major Findings** (significantly degrades experience):

1. **Heading hierarchy skips from `h1` to `h3` four times, then reverses upward to `h2` twice — the outline does not match the document's actual section structure.**
   - Evidence: Component Code (`heading-hierarchy-skipped.dump.prompt.md:11, :13, :19, :22, :29, :31, :34`) — `<h1>` (line 11) is followed directly by four `<h3>` elements ("Why Accessibility Matters" line 13, "WCAG Guidelines" line 19, "Common Issues" line 22, "Getting Started" line 29), then two `<h2>` elements ("Tools and Resources" line 31, "Conclusion" line 34). No `h2` exists between the `h1` and the first `h3`.
   - Measured confirmation: axe-core flags `heading-order` (moderate impact, selector `h3:nth-child(2)`) against `heading-hierarchy-skipped.html`. The keyboard-a11y-tester screen-reader census for the same URL independently reproduces the identical level sequence in AT reading order: index 3 "heading...level 1" → index 4 "heading...level 3" → index 8 "heading...level 3" → index 12 "heading...level 3" → index 24 "heading...level 3" → index 25 "heading...level 2" → index 29 "heading...level 2". Two independently-generated artifacts agree exactly, so this is measured fact, not design reasoning.
   - User group impacted: Screen reader users navigating by heading level (NVDA/JAWS "H" key stepping, VoiceOver rotor headings list) — a heading-level jump is the standard strategy for building a mental table of contents or skipping to "the next section at this level," and this document's marked structure actively misrepresents that: a user who jumps to `h2` first to preview the article sees only "Tools and Resources" and "Conclusion," missing the first four sections entirely, because those are marked one level lower than their actual position in the reading flow implies. Secondary impact on sighted users: because CSS assigns `h3` a smaller, gray (`#666`) treatment and `h2` a larger, blue (`#0066cc`) treatment, the first four sections render visually demoted relative to the last two, even though nothing in the content justifies treating them as a different structural tier — this is a shared visual/structural defect, not purely an assistive-technology-only concern.
   - Expected behavior: WCAG 1.3.1 (Info and Relationships) — heading levels must reflect actual content structure, increasing by one at a time with no skipped levels, so the levels convey the same hierarchy assistive technology exposes as the visual design implies.
   - Fix: Renumber to a flat, gap-free outline appropriate to six co-equal sections under one `h1` — the simplest correct fix is `h1` → `h2` × 6 (all six sections become `h2`, since none of them currently contains a nested sub-section). If "Getting Started" is intended to be a genuine sub-topic of one of the others, restructure accordingly, but do not skip a level in either direction.
   - Confidence: HIGH.
   - Calibration note (Phase 8/9): this repo's own severity scale lists "Heading hierarchy has gaps but landmark structure is clear" as a MINOR-tier example. That precondition — landmark structure being clear — does not hold here (see Finding 3 below: `landmark-one-main` and `region` are both measured violations on this same page). Because both of the two structural wayfinding strategies available to a screen reader user (heading-level navigation and landmark navigation) are simultaneously degraded rather than one compensating for the other, this finding stays at MAJOR on its own footing rather than being downgraded by pattern-matching the MINOR exemplar's surface wording without checking whether its stated condition actually applies.

**Minor Findings** (friction but workaround exists):

- **`<h3>Getting Started</h3>` (line 29) introduces no content** — the next element in the source is `<h2>Tools and Resources</h2>` (line 31), with nothing between them. This is confirmed independently: the SR census shows entry 24 ("heading, Getting Started, level 3") followed immediately by entry 25 ("heading, Tools and Resources, level 2") with no paragraph, list, or other content entry in between. A user navigating by heading lands on "Getting Started" expecting a fifth body section and instead is carried straight to the next heading — the section reads as broken or incomplete. This also directly contradicts the fixture's own claimed accessibility feature "No headings for visual styling only": a heading with zero associated content is functioning as a label/divider, not as an introduction to content, which is the same anti-pattern that claim asserts is absent. WCAG 1.3.1. Fix: either add the body content this heading is supposed to introduce, or remove/merge the heading if it is a leftover authoring stub. Confidence: HIGH on the observation; the question of authorial intent is carried to Open Questions rather than used to suppress the finding.
- **Page content is not contained within a landmark region.** axe-core reports `landmark-one-main` (moderate, selector `html`) and `region` (moderate, selector `#root`, "All page content should be contained by landmarks") against `heading-hierarchy-skipped.html`. Note that `<article>` (used correctly here as a sectioning element) does not itself satisfy this rule — `article` is not one of the ARIA landmark roles (`main`, `navigation`, `banner`, `contentinfo`, `complementary`, `search`, `region`, `form`), so a screen reader user cycling through landmarks (e.g., NVDA's "D" key, or a rotor's landmarks list) will not land on this content at all regardless of the heading fix above. WCAG 1.3.1. Fix: ensure an ancestor `<main>` (or equivalent landmark) contains this article wherever it is mounted. Confidence: HIGH that the gap is real and measured on the rendered page; MEDIUM on whether fixing it is this component's responsibility versus the surrounding page shell's — see Open Questions.

**Enhancements** (best practice not met):

- No reverse skip-link or in-page table of contents is provided for this six-section article. For longer-form reading content, a "back to top" or jump-to-section aid helps keyboard users avoid reverse-tabbing through the whole document. WCAG 2.4.1 (Bypass Blocks, informative here — the article is not long enough to make this a hard requirement, but it is a reasonable investment given six sections).
- Heading and body font sizes are specified in fixed `px` (`.blog-post h1/h2/h3/p`) rather than relative units (`rem`/`em`). Modern browser zoom (Ctrl/Cmd + `+`) scales `px` correctly and no reflow or contrast defect was measured on this page, so this is not a finding on its own — it is only worth flagging for design systems that also need to respect OS/browser base-font-size preferences independent of page zoom.

**What's Missing** (gaps, unhandled edge cases, unstated assumptions):

- No table-of-contents or section-jump aid for a multi-section article (see Enhancement above).
- No visibility into whether an ancestor supplies `<html lang>` or a `<main>` landmark — both are outside this component's own render tree, so neither is scored as a defect of `BlogPost` itself, but both are prerequisites for the page this component ships on to be fully accessible, and neither could be verified from the component alone.
- No indication in the fixture of how heading levels reach this component in a real system. As shown, the levels are hardcoded JSX literals, so the review treats the fix as a direct code edit. If a real deployment instead pipes CMS-authored rich text into this structure, the actual fix belongs partly at the content-authoring/validation layer (reject or auto-correct skipped heading levels at save time), not only in this component's markup.

- **Screen reader user**: Reading linearly (arrow-key/line-by-line), the article is fully intelligible — every heading and paragraph is announced correctly, in visual reading order, with correct list semantics (list, listitem, position/setsize for the three "Common Issues" items). The defect is specific to *structural navigation*: jumping by heading level produces a table of contents that doesn't match the actual document, and landmark navigation doesn't reach the article at all.
- **Keyboard-only user**: No findings. The component contains zero focusable elements.
- **Low vision user (200% zoom, high contrast)**: No measured defects. Layout uses a max-width container that reflows; no touch targets exist to evaluate; contrast is clean per the axe scan for this specific page.
- **Cognitive accessibility**: The visual/structural demotion of the first four sections (smaller, gray `h3`) relative to the last two (larger, blue `h2`) works against scannability for any reader trying to build a mental map of the article, independent of assistive technology.

**Verdict Justification**: REVISE, not REJECT, because nothing here blocks access outright — every word of content remains linearly reachable to every user group, and the fixes are narrow (renumber headings, resolve or fill the empty "Getting Started" section, confirm landmark containment) rather than requiring a redesign. REVISE, not ACCEPT-WITH-RESERVATIONS, because the heading-hierarchy defect is not a stylistic nitpick — it is measured on two independent artifacts, it directly undermines the one accessibility property this component claims to deliver ("headings convey information hierarchy"), and it co-occurs with an absent landmark structure rather than being offset by one (see the calibration note under the Major finding). Fixing the heading levels, resolving the "Getting Started" gap, and confirming an ancestor `<main>` would clear the path to ACCEPT.

**Open Questions (unscored)**:

- Is `<article>` in this component always mounted inside a page shell that already provides `<main>`? If yes, the landmark/region finding is a fixture-harness artifact rather than a shippable defect of `BlogPost` itself and should be downgraded further; if no, it should be treated as a real, standing gap every time this component is used as top-level content.
- Is "Getting Started" intentionally empty (e.g., a stub for content not included in this fixture, or a heading meant to introduce a widget/embed not shown here), or is its body content missing due to an authoring error? This determines whether the fix is a code change or a content-authoring correction outside this component's control.
- Does this component ever receive heading levels dynamically from CMS-authored content rather than the hardcoded JSX shown? If so, the durable fix is validation/normalization at the authoring layer, not a one-time edit to this file.
