# Accessibility Design Critic — BuggyFileInput

**VERDICT: REVISE**

**Overall Assessment**: `BuggyFileInput` correctly uses a native `<input type="file">` (no ARIA-widget reinvention) and its focus indicator is measurably clean, but the component ships with zero accessible-name, error-association, or error-announcement wiring. A screen reader or voice-control user cannot tell what the control is for beyond the browser's generic "Choose File" button chrome, and — more seriously — will not be told when an oversized file is rejected, because the error text is neither associated with the input nor placed in any live region. This is a silent-failure pattern on a single-purpose page, confirmed independently by static axe evidence, a live keyboard/screen-reader trace, and the screen-reader reading-order census. The interaction model itself does not need to change; it needs the missing semantic wiring added.

**Pre-commitment Predictions**: Before reading the code, for a "file input with client-side validation" component the expected failure modes were: (1) missing/unassociated `<label>`, (2) error not linked via `aria-describedby`, (3) error not live-announced, (4) missing `aria-invalid`, (5) file-type/size restrictions not surfaced to assistive technology. All five were confirmed. The one genuine addition from evidence rather than prediction: the keyboard-a11y-tester trace shows the computed accessible name is literally `"Choose File"` (the browser's UA-intrinsic string for the file-picker button), which turns the abstract "no label" prediction into a concrete, measured fact about what a screen reader user actually hears — and is the exact "name-presence trap" the review protocol itself calls out (a non-empty accessible name is not proof of a real label).

Evidence-pack scoping note: the pack also bundles axe-core scans for roughly seventeen unrelated sibling pages from the same batch run (`accordion-no-region-role`, `app-focus-order-illogical`, `async-form-vague-success`, `breadcrumb-navigation-no-nav-landmark`, `button-skip-link-clean`, `checkbox-group-no-fieldset`, `combobox-autocomplete-no-listbox-role`, `dashboard-heading-inconsistency`, `data-table-missing-scope`, `expandable-section-no-button`, `form-field-vs-summary-errors`, `form-validation-missing-aria-describedby`, `heading-hierarchy-skipped`, `image-carousel-no-region`, `infinite-scroll-no-announcement`, `interactive-dropdown-clean`, `interactive-dropdown-focus-bug`, `loading-state-missing-aria-busy`). None of those findings (e.g. `target-size` on the accordion/carousel buttons, `tabindex` on the focus-order page) belong to `BuggyFileInput` and none are used as evidence below. The only in-scope artifacts are the `file-input-no-labels.html` axe scan, the keyboard-a11y-tester `trace.json`, and the `sr-census.json` for that same page.

---

**Critical Findings** (blocks access):

1. **No programmatic label — accessible name is the browser's UA-default "Choose File," not the author's "Upload file" caption.** The visible caption is a bare `<div>Upload file</div>` (component source, line 19), with no `<label>`, `htmlFor`, `aria-label`, or `aria-labelledby` anywhere connecting it to the `<input type="file">` (lines 20–24). Confirmed by three independent measured sources: (a) axe-core `label` rule fired at **critical** impact against selector `input` — "Form elements must have labels" (`wcag2a`, `wcag412`; also tagged `section508`, `section508.22.n` as Revised Section 508 §1194.22(n) regulatory context, though WCAG 4.1.2/1.3.1 remain the primary citation for this component-level review); (b) the keyboard-a11y-tester driven trace (`step_0001`) shows `ax_name_role_state.name: "Choose File"`, `role: "button"` — the Chromium UA-intrinsic string for the file-picker sub-control, not a developer-supplied label; (c) the screen-reader reading-order census lists `"Upload file"` as a plain text entry (`tag: null`, `selector: null`) with no structural role, confirming it never enters the accessible name computation for the input at all.
   - Confidence: HIGH
   - Why this matters: Screen reader users hear only "Choose file, button" with no indication of what to upload or why. Voice-control/switch-access users who target controls by their visible label (e.g., saying "click Upload file") will fail, because the accessible name the browser exposes is "Choose File," not "Upload file" — a concrete, non-theoretical mismatch, not a hypothetical one.
   - Fix: Wrap the input in a real `<label>` (or use `htmlFor`/`id`) so "Upload file" becomes the input's programmatic accessible name: `<label htmlFor="file-upload-input">Upload file</label><input id="file-upload-input" type="file" ... />`. DOM-verify post-fix that the computed accessible name is now "Upload file," not "Choose File."

2. **Error message is not associated with the input and is not announced to assistive technology.** The conditional error `<div className="error-message">{error}</div>` (lines 26–28) has no `id`, so it cannot be the target of `aria-describedby`; it also has no `role="alert"`, `role="status"`, or `aria-live` attribute. The screen-reader census independently confirms `declared_live_regions: []` for this page — there is no live region anywhere in the DOM — and lists `"File too large"` as plain linear reading-order content, not a distinguished announcement. On a page whose only focusable control is the file input (the trace's `step_0002` shows the very next Tab after the input exits to `body`, i.e., there is nothing else on the page to tab back into), a user who has already moved on has no mechanism to discover the rejection short of manually re-reading the page top to bottom.
   - Confidence: HIGH
   - Why this matters: This is the textbook "form validation fails silently" case — the user may reasonably believe the upload succeeded when nothing was submitted. Screen reader users are blocked outright; sighted keyboard-only users (without a screen reader) are less affected since the red-flagged text is visually present in the same viewport.
   - Fix: Give the error container a stable `id` and reference it from the input via `aria-describedby`; additionally wrap the error text in a region that announces on appearance (`role="alert"` for this single-error-per-event case, consistent with the "one announcement region per event type, not per field" rule — this is a single non-repeating error slot, so `role="alert"` here is appropriate, not the broadcast-in-a-loop anti-pattern). DOM-verify the `aria-describedby` reference actually resolves once rendered.

**Major Findings** (significantly degrades experience):

1. **Missing `aria-invalid` on the input.** `handleFileChange` (lines 7–15) sets `error` state but never sets any ARIA validity attribute on the `<input>`. The trace's captured `states.invalid: "false"` for the pre-interaction state is consistent with this — but there is no code path anywhere in the component that would ever flip it to `"true"`, since `aria-invalid` is never referenced in the JSX at all.
   - Confidence: HIGH
   - Why this matters: A screen reader user who tabs back to the field after a rejected upload gets no programmatic signal that the field is currently in an error state — even if the announcement gap above were fixed, re-visiting the control later gives no persistent cue.
   - Fix: Add `aria-invalid={Boolean(error)}` to the `<input>`, kept in sync with the `error` state.

2. **File-type/size restrictions are never surfaced as instructions, and the error message omits the actual limit.** The `accept=".pdf,.doc,.docx"` attribute (line 23) only filters the OS file picker; it is not visible or programmatically associated instructional text, and the 5,000,000-byte (5 MB) limit (line 9) exists purely in JS logic with no corresponding UI text anywhere. When the limit is exceeded, the message is simply `"File too large"` (line 10) — it never states the actual threshold or a corrective action.
   - Confidence: HIGH on absence; MEDIUM on severity precision — mitigated by: the message is visible in the DOM to sighted users, and "pick a smaller file" is a commonly-guessable remedy even without an explicit number, so this does not reach the same "complete task failure" level as Critical Finding 2. Kept at MAJOR rather than downgraded further because the limit is never disclosed even after the failure occurs, for any user.
   - Fix: Add visible, associated instructional text near the input (e.g., "PDF or Word documents, up to 5MB," referenced via the same `aria-describedby` used for the error, or a separate hint id also included in the describedby list) and update the error copy to state the limit explicitly: `"File too large — choose a file under 5MB."` (WCAG 3.3.2 Labels or Instructions; 3.3.3 Error Suggestion.)

**Minor Findings** (friction but workaround exists):
- None identified. The gaps found in this component are substantive (Critical/Major) rather than cosmetic; there is no lower-tier polish issue worth listing separately without diluting the findings above.

**Enhancements** (best practice not met):
- Axe flags `landmark-one-main`, `page-has-heading-one`, and `region` (moderate impact, all tagged `best-practice` only — axe does not attach a WCAG success-criterion tag to any of the three for this page). These are page-shell concerns, not specific to the file-input widget, and this fixture appears to be an isolated single-component page rather than a full page template — see Open Questions. Logged as enhancement-level rather than a blocking finding pending that context.

**What's Missing** (gaps, unhandled edge cases, unstated assumptions):
- Missing field association: no `<label>`/`htmlFor`/`aria-labelledby` anywhere (Critical Finding 1).
- Missing error-to-field association: no `id` on the error container, no `aria-describedby` on the input (Critical Finding 2).
- Missing live announcement for the error: no `role="alert"`/`aria-live`, and the census confirms zero declared live regions on the page (Critical Finding 2).
- Missing `aria-invalid` state sync (Major Finding 1).
- Missing upfront instructional text for allowed file types and the size cap, and missing a specific limit/fix in the error copy itself (Major Finding 2).
- Not missing: focus management. There is exactly one focusable element; Tab reaches it and exits to `body` cleanly (trace `step_0002`), and Shift+Tab returns to it without a trap (trace `step_0003`). No modal, no dynamic focus movement is needed when the error appears, and none is attempted — this is correct, not a gap, and no focus-order finding is warranted here (WCAG 2.4.3, 2.1.2 both satisfied by the absence of any focus-moving code).
- Not missing: focus visibility. The trace measures a visible outline (`outline_color: rgb(0, 95, 204)`, `contrast: 4.86`, `contrast_pass: true`, `area_pass: true`, `aaa_pass: true`) — this comfortably passes WCAG 2.4.7 and the stricter 2.4.13 appearance thresholds. Stated here explicitly per the "if it's genuinely fine, say so" principle, not left as an implied absence of a finding.
- Not applicable: no composite ARIA widget (tabs, menu, listbox, combobox) is present, so none of the roving-tabindex / `aria-expanded` / `aria-controls` composite-pattern checks apply. This is a plain native form control, and using it as one (rather than reinventing it with `div`/`role="button"`) is the correct baseline choice.
- Not applicable: none of the nine known anti-patterns from the prior third-party audit are present in this component (no loop-scoped `aria-live`/`role="alert"`, no `title`-as-name conflation, no `aria-label`-on-wrapper masking a missing visible label, no branching logic to miss an else-case, no CMS view-mode duplication, no table markup, no images, no icon fonts). The one applicable process note: whichever fix lands for Critical/Major findings above should be DOM-verified (inspect the rendered accessibility tree) to confirm the `id`/`aria-describedby` reference actually resolves and `aria-invalid` actually flips — not just eyeballed in the JSX diff.
- Known-false-positive check: none of this review's findings match the listed false-positive patterns (no `jsx-a11y/no-noninteractive-element-interactions` role pass-through, no Next.js `<Link>`-as-anchor case, no gradient/transparent-background contrast ambiguity, no React-portal region situation, no spread-prop `aria-allowed-attr` case). The axe `label` violation is a clean true positive that matches the source directly.

**Multi-Perspective Notes**:

| Perspective | Alarm Level | Trigger Signal |
|-------------|-------------|----------------|
| Screen reader | HIGH | No real accessible name (UA-default "Choose File" only), unassociated + unannounced error, no `aria-invalid` — blocks task completion and error recovery |
| Keyboard-only | LOW | Full keyboard operability confirmed by trace; visible, high-contrast focus indicator measured clean; no trap |
| Low vision | MEDIUM | No zoom/reflow evidence was measured either way (open question); restriction text is absent for every user, not just AT users |
| Cognitive | MEDIUM | Vague error message with no stated limit or corrective action; constraints only discoverable by trial and failure |
| Vestibular & motion | LOW | No animation, transition, or auto-playing content in this component |
| Auditory access | LOW | No audio/video elements present |
| Environmental contrast | LOW | No color-contrast violation measured for this page; state is not conveyed via color alone |

- **Screen reader user**: Tabs to the control and hears "Choose file, button" — nothing ties this to "Upload file," and nothing conveys the type/size restrictions before acting. If an oversized file is chosen, "File too large" appears on screen but the census confirms no live region exists to announce it and the trace shows the input is the only stop on the page (nowhere to naturally tab back through to rediscover it). This user can plausibly walk away believing the upload succeeded.
- **Keyboard-only user**: Fully operable — Tab reaches the single control, Shift+Tab returns without a trap, and the measured focus outline (contrast 4.86, area and AAA-appearance thresholds both passing per the trace) is unambiguous. A sighted keyboard-only user (not also relying on a screen reader) will see the red-flagged error text in place, so the state-communication gap above is chiefly an assistive-technology problem here, not a keyboard-operability one.
- **Low vision user (200% zoom, high contrast)**: No zoom/reflow or forced-colors test exists in the evidence pack, so no measured claim can be made either way — logged as an open question rather than assumed clean or broken. Axe's contrast checker did run against this page and raised no `color-contrast` violation for the error text, so that specific dimension has been checked, not merely assumed.
- **Cognitive accessibility**: The error is vague ("File too large" with no number and no fix) and the restriction (types, 5MB cap) is never stated up front — both push the user toward a guess-and-check loop rather than clear, actionable instructions (WCAG 3.3.2, 3.3.3).

**Verdict Justification**: REVISE, not REJECT — the underlying pattern (a native `<input type="file">` plus a conditionally-rendered inline error) is the right architecture and does not need to be redesigned; it needs the missing semantic wiring added: a real `<label>`, an `id`+`aria-describedby` link from the input to both the error and a restrictions hint, a `role="alert"` (or equivalent live announcement) on the error container, a synced `aria-invalid`, and error copy that states the actual limit. Two findings are rated CRITICAL because they meet the protocol's own bar for that tier verbatim ("form validation fails silently," "blocks access entirely for a user category") and are corroborated by three independent measured sources (axe critical impact, live keyboard/SR trace, reading-order census) rather than code-reading alone — this is exactly the kind of case where test evidence upgrades a design-reasoning claim into a measured fact. The Screen Reader perspective is rated HIGH alarm, which under this protocol's own escalation rule is a signal to route this component through `/perspective-audit` before it ships, given the finding blocks a complete user category from finishing the one task the page exists to support. Upgrade path: fixing both CRITICAL findings and DOM-verifying the attribute wiring would support ACCEPT-WITH-RESERVATIONS; addressing the MAJOR restriction/error-copy gaps as well would support full ACCEPT. Nothing here was downgraded from CRITICAL for the two access-blocking findings, consistent with the rule against softening findings that amount to complete access loss; the restriction/error-copy finding was deliberately kept at MAJOR rather than CRITICAL with its mitigation stated explicitly, and the page-shell landmark/heading axe findings were deliberately kept at enhancement level pending confirmation of this fixture's embedding context, to avoid inflating a component-scope review with what may be page-template-level absences.

**Open Questions (unscored)**:
- Is `BuggyFileInput` always rendered standalone, or is it normally embedded inside a page shell that already supplies `<main>`, a landmark structure, and an `<h1>`? The axe `landmark-one-main` / `page-has-heading-one` / `region` findings may be artifacts of testing this component in isolation rather than real page-level gaps — needs developer confirmation before being treated as findings against this component itself.
- Reflow and readability at 200% zoom and behavior under forced-colors/Windows High Contrast mode were not exercised by any tool in this evidence pack. No claim is made either way; a dedicated check is recommended before sign-off rather than assuming either outcome.
- The keyboard-a11y-tester trace's `sr_announcement.focus_announcement` field reads `"document"` on the very first Tab into the page's only focusable control, rather than reflecting the `"Choose File"` name captured in the same step's `ax_name_role_state`. This review relied on the `ax_name_role_state` field (the more direct signal for computed accessible name) for Critical Finding 1, since it is the field that most directly answers "what name is exposed." The discrepancy between the two fields in the same trace step is flagged as worth clarifying with whoever maintains the tracing harness — it is not treated as an independent defect of the component.
- No `<form>` element or submit control appears anywhere in the 34-line source — it is unclear how or whether the selected file is ever sent anywhere beyond local component state. This is outside a11y-critic's scope as a functional-completeness question, but it is worth flagging to the developer since it may affect how far downstream the `aria-describedby`/live-region recommendations above need to extend (e.g., whether a later submit step introduces its own, separate error-communication surface).
