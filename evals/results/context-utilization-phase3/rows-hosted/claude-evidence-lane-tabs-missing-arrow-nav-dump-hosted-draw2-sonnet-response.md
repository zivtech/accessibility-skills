**VERDICT: REVISE**

**Overall Assessment**: The `TabsWidget` component gets the ARIA skeleton right — correct roles, correctly-wired `aria-selected`/`aria-controls`/`aria-labelledby`, real `<button>` elements, a visible focus style, and roving `tabindex` markup. But the keyboard interaction layer on top of that skeleton is broken in two compounding ways: arrow-key navigation was never implemented (measured directly in the attached driven trace), and the Enter/Space handler contains an id-format bug that, on inspection, appears to reset selection to an invalid state on every keyboard activation attempt. Because roving `tabindex` deliberately removes the two inactive tabs from the Tab sequence, the missing arrow-key support isn't a "rough edges" problem — it makes 2 of the widget's 3 tab panels completely unreachable by keyboard.

**Evidence Scope Note (Phase 0)**: The evidence pack bundles one directly relevant artifact — `evals/results/keyboard-a11y-tester/driven/tabs-missing-arrow-nav.trace.json`, a driven keyboard+screen-reader session against this exact component (`start_url: .../tabs-missing-arrow-nav.html`, `goals: [{"intent": "navigate between tabs using arrow keys"}]`) — treated below as hard, measured evidence per the trace's step-by-step facts. Every other JSON block in the pack is explicitly labeled "(sibling page)" and points at unrelated fixture URLs (`accordion-no-region-role.html`, `async-form-vague-success.html`, `dashboard-heading-inconsistency.html`, `pagination-no-nav-landmark.html`, etc.). One of these, `tabs-incomplete-aria-selected.json`, is a same-family but *different* fixture (`tabs-incomplete-aria-selected.html`, not `tabs-missing-arrow-nav.html`) and is the one most likely to get misattributed given the similar name — its findings (a missing accessible name on `#panel-1`, weak focus contrast on `#tab-1`) are **not** evidence about the component under review here. I'm using it only as comparison context below (our component's panels *do* have `aria-labelledby`, so the accessible-name gap seen in that sibling fixture does not reproduce here) — not as a finding against this code. No other sibling artifact is used as evidence in this review.

**Pre-commitment Predictions**: Before digging into the code, for a custom tabs widget I'd expect to find: (1) missing or partial arrow-key navigation — the single most common Tabs-pattern gap; (2) roving `tabindex` present in markup but not actually paired with a working key handler that moves focus; (3) `aria-selected` toggling on click but drifting out of sync under some path; (4) `aria-controls`/`aria-labelledby` id references that look right in the JSX but don't actually resolve to real DOM ids; (5) no clear choice of activation model (automatic vs. manual per WAI-ARIA APG). Investigation confirmed (1) and (2) directly, found (3) and (4) to actually be correct (worth crediting, not assuming), and surfaced something *not* on this list and more severe than any of it: the existing Enter/Space handler doesn't just lack a feature, it actively miscomputes the tab index on every keyboard activation.

**Critical Findings** (blocks access):

1. **Roving-tabindex tabs are unreachable by keyboard — arrow key navigation is not implemented.**
   - Evidence: `tabs-missing-arrow-nav.dump.prompt.md:17-22` — `handleTabKeyDown` only branches on `e.key === 'Enter' || e.key === ' '`; there is no `ArrowLeft`/`ArrowRight`/`Home`/`End` case. Meanwhile `tabs-missing-arrow-nav.dump.prompt.md:34` gives the active tab `tabIndex={0}` and every other tab `tabIndex={-1}` (roving tabindex), which is *correct* WAI-ARIA APG markup but only works if arrow keys move both focus and the roving index.
   - Measured confirmation (driven trace, `tabs-missing-arrow-nav.trace.json`): `step_0001` (Tab) lands on `#tab-overview`, `sr_announcement.focus_announcement: "tab, Overview, selected, 1 control, position 1, set size 3"` — the AT correctly hears "position 1... set size 3," i.e. it knows two more tabs exist. `step_0002` (ArrowRight) and `step_0003` (ArrowLeft) both report `"focus_moved": false`, `active_element_selector` unchanged, and `sr_announcement.new_phrases: []` — direct, measured proof arrow keys are a no-op. `step_0004` (Tab) then reports `active_element_selector: "body"` — focus leaves the tablist entirely, confirming Tab does not enumerate the other two tabs (correct roving-tabindex behavior *if* arrows worked; here it just means the tablist is exited without ever reaching them).
   - User group impacted: keyboard-only users (no path to tabs 2/3 at all) and, likely, screen-reader users navigating by Tab/Arrow — the pattern's documented interaction model. A screen-reader user who knows to fall back on AT-specific object/rotor navigation might still reach the other tab buttons through the accessibility tree independent of `tabindex`, but that's an AT-specific workaround the design doesn't provide or guarantee, not a substitute for a working arrow-key implementation.
   - Expected behavior: Per the WAI-ARIA APG **Tabs (Tab Panel) pattern**, when a tab has focus, `ArrowRight`/`ArrowLeft` must move focus to the next/previous tab (with wraparound), and `Home`/`End` should jump to the first/last tab. WCAG **2.1.1 Keyboard** — all functionality (viewing every tab's content) must be operable through the keyboard; right now it isn't.
   - Confidence: HIGH (measured directly by the driven trace, not inferred).
   - Why this matters: this isn't "arrow keys would be nicer" — because the inactive tabs are removed from the Tab sequence by design, arrow keys are the *only* documented keyboard path to them. Without that path, 2 of 3 tab panels' content is categorically unreachable for a keyboard-only user, not merely awkward to reach.
   - Fix: give `handleTabKeyDown` the tab's own `index` (the same value `onClick` already correctly closes over at `tabs-missing-arrow-nav.dump.prompt.md:35`) and branch on the arrow/Home/End keys:
     ```jsx
     const tabRefs = useRef([]);

     const handleTabKeyDown = (e, index) => {
       const last = tabs.length - 1;
       let next;
       switch (e.key) {
         case 'ArrowRight': next = index === last ? 0 : index + 1; break;
         case 'ArrowLeft':  next = index === 0 ? last : index - 1; break;
         case 'Home':       next = 0; break;
         case 'End':        next = last; break;
         case 'Enter':
         case ' ':
           e.preventDefault();
           handleTabClick(index);
           return;
         default:
           return;
       }
       e.preventDefault();
       handleTabClick(next);
       tabRefs.current[next]?.focus();
     };
     ```
     and wire it as `onKeyDown={(e) => handleTabKeyDown(e, index)}` plus a `ref` callback per button. The explicit `.focus()` call matters — updating `tabIndex` via state alone does not move DOM focus; without it the roving-tabindex markup would update but the user's focus would stay stuck on the now-`tabindex="-1"` button. Decide and document whether this is "automatic activation" (shown above — arrowing also selects the panel immediately) or "manual activation" (arrow keys only move focus; Enter/Space selects) per APG; the sketch above implements automatic activation, which matches how `aria-selected` is currently wired directly to `activeTab`.

2. **Enter/Space activation resets selection instead of switching tabs — id-format mismatch in `handleTabKeyDown`.**
   - Evidence: `tabs-missing-arrow-nav.dump.prompt.md:20` — `handleTabClick(tabs.findIndex(t => t.id === e.currentTarget.id))`. `e.currentTarget.id` is the *DOM* id, rendered at `tabs-missing-arrow-nav.dump.prompt.md:30` as `` id={`tab-${tab.id}`} ``, e.g. `"tab-overview"`. But `t.id` inside the `findIndex` callback is the raw data id, e.g. `"overview"` — the exact same field the template literal is built from. `"overview" === "tab-overview"` is never true for any tab, so `findIndex` always returns `-1`, and every Enter/Space press calls `handleTabClick(-1)` → `setActiveTab(-1)`. With `activeTab = -1`: `aria-selected={index === activeTab}` (line 32) is `false` on every tab, and `hidden={index !== activeTab}` (line 51) is `true` on every panel — the entire widget collapses to "nothing selected, nothing visible."
   - Corroboration from the trace: `step_0001`'s `active_element_selector` is exactly `"#tab-overview"` (a single `tab-` prefix), which is only consistent with `tab.id` being the bare value (`"overview"`) — confirming the mismatch this bug depends on is real, not a misreading of the source.
   - Why keyboard users hit this even though the button is a native `<button>`: a native button already activates on Enter (click fires as keydown's default action) and Space (click fires on keyup). Because `handleTabKeyDown` unconditionally calls `e.preventDefault()` for both keys before running its own broken dispatch (line 19), it suppresses the button's correct native activation and replaces it with the broken one. The working `onClick={() => handleTabClick(index)}` at line 35 is bypassed entirely for keyboard activation — mouse clicks are unaffected, since they never go through `handleTabKeyDown`.
   - Evidence tier: HIGH confidence from the code logic itself (a plain string-equality bug, not a subtle runtime nuance), but **not yet directly measured** — the attached driven trace only exercises `Tab`/`ArrowRight`/`ArrowLeft`/`Tab`, not `Enter`/`Space`. Flagging this explicitly rather than presenting it as a measured fact; recommend a follow-up driven run that sends `Enter` and `Space` on a focused tab and asserts `aria-selected`/`hidden` afterward.
   - User group impacted: every keyboard-only and screen-reader user attempting to activate a tab via keyboard — including on the tab that's already active (this bug isn't limited to "switching" tabs; pressing Enter on the currently-selected tab triggers the same reset).
   - Expected behavior: WCAG **2.1.1 Keyboard** — keyboard activation must perform the same operation as the equivalent mouse click; here it performs a destructive, different operation. Resulting state also violates **4.1.2 Name, Role, Value** — a tablist should never land in a state where no tab has `aria-selected="true"`.
   - Fix: see the code sketch under Finding 1 — routing Enter/Space through the same closed-over `index` that `onClick` already uses (`handleTabClick(index)`) removes the broken `findIndex` call entirely; no lookup by id is needed at all.

**Major Findings** (significantly degrades experience): None. Everything else that could plausibly rise to MAJOR (activation-model ambiguity, Home/End) is either resolved as part of fixing the two Critical findings above or is narrow enough to land at MINOR — see below. I'm not manufacturing a middle tier just to have one.

**Minor Findings** (friction but workaround exists):
- Missing `Home`/`End` key support (jump to first/last tab). Distinct from Finding 1's core Left/Right gap — once Left/Right work, a user can still reach any tab by repeating Right/Left, so this is a convenience gap, not a lockout. Per WAI-ARIA APG Tabs pattern, recommended but not the load-bearing requirement Left/Right is.
- No explicit `aria-orientation` on the tablist (`tabs-missing-arrow-nav.dump.prompt.md:26`). The default is `horizontal`, which matches the actual layout (`[role="tablist"] { display: flex; }`, no `flex-direction: column`), so this isn't a defect today — flagging only because it's worth setting explicitly once arrow-key handling is added, so the key mapping (Left/Right vs. Up/Down) stays self-documenting if the layout ever changes.

**Enhancements** (best practice not met, no access barrier):
- Consider `tabIndex={0}` on each `tabpanel` if a panel's content ever has no focusable descendant (currently just a `<p>`), so keyboard users can Tab directly into panel content rather than relying on AT browse-mode to reach it. Conditional on real content — not asserting this as a current defect since screen-reader virtual-cursor navigation typically reaches static text regardless of tab order.
- Once arrow-key handling is added, add a short code comment stating which activation model (automatic vs. manual, per WAI-ARIA APG) was chosen and why — this component's `aria-selected` is currently wired directly to `activeTab` with no separate "focused but not yet selected" state, which only makes sense under automatic activation; making that explicit prevents a future contributor from half-implementing manual activation on top of it.

**What's Missing** (gaps, unhandled edge cases, unstated assumptions):
- No working keyboard path to change tabs at all: arrow keys are absent (Finding 1) and the Enter/Space fallback is broken (Finding 2). Only a mouse click reliably switches tabs today.
- No `Home`/`End` support (Minor, above).
- No stated activation-model decision — the code's current wiring only makes sense for automatic activation, but nothing says so explicitly.
- No test coverage exercising `Enter`/`Space` on a tab button — the attached trace's goal was specifically arrow-key navigation, so the Enter/Space defect has no measured artifact yet; it was found only by reading the source against the trace's confirmed DOM ids.

**Multi-Perspective Notes**:
- **Screen reader user**: The one reachable tab announces well — `"tab, Overview, selected, 1 control, position 1, set size 3"` (measured) correctly conveys role, name, selected state, the panel relationship, and the group size, so a screen-reader user knows two more tabs exist. But they have no confirmed way to reach them via the documented Tab/Arrow model (arrow keys measured as no-ops), and if they reflexively press Enter/Space on the tab they're already on, Finding 2 (unmeasured but high-confidence) would silently blank the tablist's selection and hide all panel content — a confusing, hard-to-diagnose failure purely from audio feedback, since nothing is announced when it happens (the trace shows no `sr_announcement` at all on the failed arrow presses, and the Enter/Space collapse wouldn't announce anything either, since no `aria-live` region exists to narrate it).
- **Keyboard-only user**: Tab reaches exactly one tab ("Overview"). Arrow Left/Right do nothing (measured). A second Tab press exits the tablist entirely rather than reaching tab 2 or 3 (measured). There is currently no keyboard route to the other two tabs' content at all. The focus indicator itself is solid — real CSS `outline` (not `box-shadow`, which some layouts clip), 3px, `#0066cc`, matching the trace's `computed_focus_style` and clearing contrast comfortably (measured `contrast: 5.56` against the page background).
- **Low vision user (200% zoom, high contrast)**: Focus indicator uses an outline with `outline-offset`, which survives zoom and forced-colors mode better than a `box-shadow`-only approach. Active-tab state is signaled redundantly — color change, `font-weight: 600`, and a `border-bottom` — not color alone, satisfying WCAG 1.4.1. Text contrast is comfortable: `#666` and `#0066cc` against an unset (effectively white) background both clear 4.5:1. Touch/click target size is generous — the trace's measured `bounding_box` for the Overview tab is `111.15625 × 45`px, well past the 24×24 minimum and the 44×44 recommendation (WCAG 2.5.8). The trace's AAA-tier `focus_appearance` numbers (`aaa_pass: false` at step 1, `true` at step 3) look like a frame-diffing artifact of the tool rather than a real change in the widget — nothing in the DOM changes between those steps besides two no-op arrow presses — and 2.4.13 is AAA-only in any case, so this project's WCAG 2.2 AA target isn't affected either way; noting it for transparency, not as a graded finding.
- **Cognitive accessibility**: Beyond the operability failures already covered, the *unpredictability* compounds the problem: arrow keys silently do nothing (no error, no feedback), and Enter/Space (if Finding 2 reproduces) silently destroys all visible state with no explanation. Silent, state-destroying failures with no error message are exactly the kind of unpredictable interaction that's disproportionately costly for cognitive-disability users, even though it isn't cleanly mapped to a single WCAG SC beyond the keyboard-operability citations already given.

**Verdict Justification**: Two CRITICAL findings block core functionality for keyboard-only and likely screen-reader users, so this cannot ship as-is. I'm rating REVISE rather than REJECT because the underlying design decisions are sound and don't need to be re-architected: the ARIA pattern choice (Tabs/Tab Panel), the semantic HTML (real `<button>`s, no div-as-button), the id-based `aria-controls`/`aria-labelledby` wiring, and the roving-tabindex markup are all correct per WAI-ARIA APG. Both defects are narrow, well-understood code fixes layered on that correct foundation — add arrow/Home/End handling, and stop routing keyboard activation through a broken `findIndex` when the correct index is already sitting in the same closure `onClick` already uses. Recalibration disclosed: the protocol's own worked example ("tabs with `aria-selected` but no arrow keys... Reports as MAJOR") would default this to MAJOR; I upgraded Finding 1 to CRITICAL specifically because roving `tabindex` is *already implemented* here, so the missing arrow keys don't just make the widget "confusing" — combined with roving tabindex they make 2 of 3 tabs categorically unreachable, which meets this protocol's own CRITICAL bar ("blocks access entirely for a user category") rather than MAJOR's "significantly degrades experience." Nothing here was downgraded. What would move this to ACCEPT-WITH-RESERVATIONS: both Critical findings fixed and re-verified with a driven keyboard trace exercising Arrow keys in both directions and Enter/Space on both the active and an inactive tab, confirming `aria-selected`/`hidden`/focus location all update correctly and that no state resets to an invalid `-1` index.

**Open Questions (unscored)**:
- Does the production deployment of this widget assume screen-reader users will fall back on AT-specific rotor/object navigation to reach tabs 2 and 3, bypassing the broken arrow-key path? If that assumption exists anywhere in product decisions, it should be validated with real AT testing rather than assumed — browse-mode reachability of `role="tab"` elements outside the Tab sequence is not guaranteed to be consistent across NVDA/JAWS/VoiceOver.
- Would `tab.content` in real use ever contain interactive elements (links, buttons) inside a panel? If panels are ever plain static text only, the `tabIndex={0}`-on-tabpanel enhancement noted above becomes more directly relevant; if panels always contain focusable content, it's moot. Not verifiable from this fixture alone.
- Finding 2 (Enter/Space bug) is HIGH confidence from code inspection and corroborated indirectly by the trace's confirmed DOM id format, but has no direct keyboard-press measurement in the attached evidence. Recommend confirming with an actual driven Enter/Space test before treating it as fully proven in a fix ticket.
