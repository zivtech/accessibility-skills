**VERDICT: REVISE**

**Overall Assessment**: The component's ARIA structure (tablist/tab/tabpanel roles, `aria-selected`, `aria-controls`/`aria-labelledby` pairing, roving-tabindex attributes, native `hidden` panel-hiding) is well-formed, correctly wired, and — where the evidence pack speaks to it — confirmed correct at runtime. The design fails on exactly one axis, but that axis is load-bearing for the entire widget: `handleTabKeyDown` only recognizes `Enter` and `Space`. No `ArrowLeft`/`ArrowRight` handling exists anywhere in the component, so the roving-tabindex mechanism has no driver. A keyboard-only or screen-reader user who reaches this tablist can operate exactly one tab — whichever one currently holds `tabIndex={0}` — and has no way to reach the others. That is not a partial ARIA pattern; it is a complete keyboard-operability failure for a specific population, sitting inside an otherwise sound implementation.

**Pre-commitment Predictions**: Before reading the code closely, the expected failure modes for a hand-rolled Tabs widget were: (1) arrow-key navigation missing or incomplete, (2) roving tabindex present as markup but not actually driven by a key handler, (3) ambiguity between the manual- and automatic-activation models, (4) `aria-selected` not reliably reflecting state, (5) `aria-controls`/`aria-labelledby` pointing at the wrong or stale ids.

Findings 1 and 2 were confirmed, and turned out to be the same defect: no handler exists to drive the roving tabindex, so it never roves past the initially-active tab. Finding 3 is confirmed in a specific sense: the code satisfies neither activation model, because the movement step both models depend on doesn't exist. Findings 4 and 5 were **not** confirmed — they were actively disconfirmed by both source inspection and the digest's trace excerpt (`aria-selected` and `aria-controls` are correct and, per the digest, DOM-verified live). The rest of the implementation — native `<button>` elements, correct `hidden` usage, visual+programmatic state pairing, no anti-pattern hits from the April 2026 known-defect list — was cleaner than the median prediction for this component type.

**Critical Findings** (blocks access):

1. **Roving-tabindex Tabs pattern has no keyboard driver — Left/Right Arrow do nothing, and no other tab is keyboard-reachable.** See `TabsWidget`, `handleTabKeyDown` (component source as provided, lines 17–22): the only branch is `e.key === 'Enter' || e.key === ' '`, which re-invokes `handleTabClick` on whichever tab is `e.currentTarget` — i.e., the tab that already has focus. There is no `ArrowLeft`/`ArrowRight` (or `Home`/`End`) branch anywhere in the component. Combined with `tabIndex={index === activeTab ? 0 : -1}` (line 34) correctly implementing roving tabindex *at the attribute level*, the practical effect is: exactly one `<button role="tab">` is ever in the page's Tab sequence at a time (the active one), and nothing in the component can move focus, or trigger a panel switch, for any other tab via keyboard. Clicking is the only way to reach tabs 2..n.
   - Evidence (digest-only, not independently re-fetched — see Evidence Consulted above): per the supplied digest of `tabs-missing-arrow-nav.trace.json`, `step_0002` (keystroke `ArrowRight`) and `step_0003` (keystroke `ArrowLeft`) both report `active_element_selector:"#tab-overview"` and `focus_moved:false`, while the two `Tab`-keystroke steps (`step_0001`, `step_0004`) both report `focus_moved:true`. The digest also reports the AX `states` dict for `#tab-overview` (role "tab", name "Overview", `selected:true`, `controls:"panel-overview"`) as byte-identical across `step_0001`–`step_0003` — consistent with focus, and therefore state, never changing in response to either arrow key.
   - User group impacted: keyboard-only users (motor/dexterity disabilities, switch-access and eye-tracking device users, and anyone who simply doesn't use a mouse) and screen reader users navigating with standard keyboard commands — which is the default interaction mode for a tablist under every major screen reader (NVDA, JAWS, VoiceOver all pass arrow keys through to the page for a native tablist; this isn't an AT-specific quirk, it's the universal expectation the APG pattern exists to satisfy).
   - WCAG/APG: **WCAG 2.2 § 2.1.1 Keyboard (Level A)** — the function of switching to tab 2 or tab 3 has no keyboard operation. Per **WAI-ARIA APG Tabs Pattern**, "Keyboard Interaction," Left/Right Arrow (for a horizontal tablist) must move focus among tabs; that requirement is unmet in full, not partially. Note: this is *not* a WCAG 2.1.2 No Keyboard Trap violation — focus is never stuck; `Tab` still moves forward and out of the widget (confirmed by `step_0004`). The bug is operability of a function, not escapability, and I want that distinction on the record rather than reflexively citing 2.1.2.
   - Confidence: HIGH. The absence is provable from the source alone (no arrow-key branch exists in the only keydown handler in the file), independent of the digest; the digest corroborates it at runtime.
   - Why this matters: a sighted mouse user experiences this component as three working tabs. A keyboard-only or screen-reader user experiences it as a single-tab widget that happens to announce "position 1, set size 3" — telling them content exists that they have no way to reach. That gap between what's announced and what's operable is a particularly bad failure mode: it's discoverable (the user knows they're missing something) but not solvable by the user.
   - Fix: in `handleTabKeyDown`, add `ArrowRight`/`ArrowLeft` (and, for completeness, `Home`/`End`) branches that compute the next index (wrapping at the ends, per APG convention), call `.focus()` on the corresponding tab button (a ref or `document.getElementById`/`querySelector` on `tab-${tabs[nextIndex].id}` both work), and update `activeTab` — either immediately (automatic activation, matching the "Arrow Left/Right should cycle through tabs" language in this fixture's own Expected Behavior) or only on a subsequent `Enter`/`Space` (manual activation). Either is APG-conformant; what's not conformant is doing neither. Call `e.preventDefault()` on the arrow keys as well, to prevent any incidental scroll.

Everything else reviewed — semantic HTML choices, ARIA attribute correctness and DOM-verified wiring, state communication for the selected state, and the full April-2026 known-anti-pattern checklist — came back clean, which is why this is REVISE and not REJECT: the fix is narrow, well-understood, and doesn't require rethinking the component's structure, only adding the one missing interaction handler. Upgrade path to ACCEPT: implement Left/Right (and ideally Home/End) arrow-key focus movement wired to the existing roving-tabindex state, verify with a re-run keyboard trace or `npx playwright test`, and confirm the HIGH-alarm screen reader/keyboard perspectives clear on re-review.
