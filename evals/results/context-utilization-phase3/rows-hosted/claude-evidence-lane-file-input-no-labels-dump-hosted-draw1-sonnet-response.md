**Overall Assessment**: `BuggyFileInput` gets the native-semantics call right — it uses a real `<input type="file">` rather than reinventing a widget with ARIA, and the measured keyboard/focus evidence is clean. But the component has no real accessible label (screen reader users get only the generic browser-default "Choose File" name) and its validation error is invisible to assistive technology: no live region, no `aria-describedby`, no `aria-invalid`. Both defects are independently confirmed by axe-core (critical-impact "label" violation) and by the keyboard-a11y-tester census (zero declared live regions, zero ARIA refs anywhere on the page). This is a "revise before shipping" component, not a "start over" one — the fixes are narrow and standard.

**Pre-commitment Predictions**: For a file-input-with-validation component, before reading the code I expected to find: (1) an unassociated or missing label — file inputs are notorious for looking "labeled enough" because of their UA-default text; (2) an error message not wired to the input via `aria-describedby`; (3) no live region / `role="alert"` for the error, so screen reader users miss validation failures; (4) `aria-invalid` never toggled; (5) no upfront disclosure of the validation constraint (file size/type) before the user acts. All five were confirmed. Two things surprised me and were not predicted: (a) an "else-branch coverage" state-desync bug — the error branch never resets `selectedFile` or the native input's displayed value, so the visible file-picker text and the app's internal state can diverge after a rejection; (b) the file input's measured bounding box is 21px tall, under the WCAG 2.5.8 24px target-size minimum — though this is very likely covered by 2.5.8's "User Agent Control" exception since no custom sizing CSS is present, so I did not score it as a violation.

**Critical Findings** (blocks access):

1. **No real accessible label — only the generic UA-default name is exposed.** The visible text `<div>Upload file</div>` (component source, line 26) sits immediately before `<input type="file" onChange={handleFileChange} accept=".pdf,.doc,.docx" />` (lines 27–31), but nothing connects them: no `<label>` wrapping or `htmlFor`/`id` pair, no `aria-label`, no `aria-labelledby`. Confirmed by axe-core: `"id": "label", "impact": "critical", "help": "Form elements must have labels", "node_count": 1, "sample_selectors": ["input"]` — the single flagged node is this exact input. The keyboard-a11y-tester trace shows the input does have *a* name via the browser's own default: `"ax_name_role_state": {"name": "Choose File", "role": "button", ...}` (trace.json step_0001/step_0003). That UA-intrinsic name is exactly the trap: it makes the control sound "labeled" in a cursory read, but it describes the generic *mechanism* ("choose a file"), never the *purpose* of this specific field. A screen reader user navigating by forms-mode/Tab (which skips non-field content, including the unassociated "Upload file" div) hears only "Choose File, button" with zero context about what they're uploading or why. Users in linear/browse-mode get partial, DOM-adjacency-based mitigation (they'd read "Upload file" immediately before "Choose File, button"), but that is an incidental coping mechanism, not a designed one, and forms-mode navigation is common enough that this does not earn a downgrade.
   - Confidence: HIGH
   - User group impacted: Screen reader users (primary); also low-vision users relying on browser "find in page" or accessibility-tree inspection, since there is no programmatic name to search by beyond the browser default.
   - Why this matters: Per WCAG 1.3.1 (Info and Relationships) and 3.3.2 (Labels or Instructions), form fields must have a programmatically associated label describing their purpose — not merely an accessible name of any kind. Per WCAG 4.1.2 (Name, Role, Value), the accessible name must be meaningful, and "Choose File" is a mechanism name, not a purpose name.
   - Fix: Wrap the input in a `<label>` (e.g., `<label htmlFor="file-upload-input">Upload file</label>` + `id="file-upload-input"` on the input), or use `aria-labelledby` pointing at the existing text node's `id`. After the fix, DOM-verify (per the protocol's anti-pattern #9) that the accessible name computed for the input actually changes from "Choose File" to the new label text — many browsers append rather than replace the UA default, so verify in DevTools' Accessibility pane, not just visually.

2. **Validation error is rendered but never announced or associated — form validation fails silently for assistive technology.** The error markup (`<div className="error-message">{error}</div>`, lines 32–36) is a plain conditionally-rendered `<div>` with no `role="alert"`/`role="status"`, no `aria-live`, no `id` for `aria-describedby` to target, and the input itself never receives `aria-describedby`. This is confirmed at the DOM level, not just from source: the keyboard-a11y-tester census (`sr-census.json`) declares `"declared_live_regions": []` and `"declared_broken_aria_refs": []` for the whole page — there are zero live regions and zero ARIA references anywhere in the rendered DOM, consistent with the source containing none. The census does capture "File too large" as a plain reading-order entry (`entries[2]`), confirming the text is present in the DOM once the error state fires — but with no live region and no focus movement toward it, a screen reader user who has just interacted with the file input (the normal, expected user flow) receives zero automatic signal that anything happened. They would have to manually re-read forward past their current position to discover the error at all.
   - Confidence: HIGH
   - User group impacted: Screen reader users (primary) — this is also a UX gap for anyone not visually scanning the page after choosing a file (e.g., users who look away, users with cognitive load issues who don't immediately re-check the screen).
   - Why this matters: WCAG 4.1.3 (Status Messages) requires that status messages — including validation errors — be programmatically determinable through role or properties such that assistive technologies can announce them without receiving focus. This finding is the almost-verbatim CRITICAL example from this protocol's own severity scale: "Form validation fails silently."
   - Fix: Give the error container a stable `id`, add `role="alert"` (or wrap it in a `aria-live="assertive"` region, since a size-rejection is an urgent, blocking error) and add `aria-describedby={errorId}` on the `<input>` whenever `error` is truthy. Per the "Broadcast vs. Association" anti-pattern check: this is a single top-level error message for one field, so `role="alert"` here is appropriately scoped (it would be a defect only if this pattern were duplicated per-row in a list/loop).

**Major Findings** (significantly degrades experience):

1. **`aria-invalid` is never wired to the validation state.** The component source (lines 14–22) never sets `aria-invalid` at all — there is no attribute in the JSX to toggle. The keyboard-a11y-tester trace shows `"states": {"invalid": "false", ...}` at both captured focus events (step_0001, step_0003), which is the browser's default computed value in the absence of any `aria-invalid` attribute; note the trace never captures a moment *after* an oversized file was actually rejected, so this specific data point is consistent with, but does not independently prove, the absence of live toggling. The source code is the primary evidence here: there is no code path anywhere that sets `aria-invalid="true"` when `error` is truthy or removes/sets `"false"` when it clears.
   - Confidence: HIGH (source-code evidence); the trace data is supporting/consistent context, not independent proof of the post-error state.
   - User group impacted: Screen reader/AT users who rely on persistent, queryable field-validity state (e.g., "jump to next invalid field" commands, or simply re-checking a field's state after navigating away and back) rather than a one-time announcement.
   - Why this matters: WCAG 4.1.2 (Name, Role, Value) requires state to be programmatically determinable, and this is state a user can query at any time — independent of whether they were present to hear a live announcement when it first fired.
   - Fix: Set `aria-invalid={!!error}` (or `"true"`/`"false"` strings) on the `<input>`, kept in sync with the `error` state.

2. **State desync between the native file-input display and the app's own `selectedFile`/error state on the rejection path ("else-branch coverage" anti-pattern).** In `handleFileChange` (lines 14–22), the success branch (lines 18–21) calls both `setSelectedFile(file)` and `setError(null)`, but the rejection branch (lines 16–17) only calls `setError('File too large')` — it never resets `selectedFile`, and it never resets the native `<input>`'s own DOM value. The keyboard-a11y-tester trace's `text` field for the focused input shows `"C:\\fakepath\\quarterly-report.pdf"` (step_0001/step_0003) — the browser's native file-input widget always displays whatever file the OS dialog returned, regardless of the app's validation outcome. That native display is not fully within the app's control, but the app's own React state (`selectedFile`) is: if a rejected file leaves `selectedFile` holding a stale previous value (or `null`) while the visible/native control still shows the rejected filename, any downstream consumer of `selectedFile` (a submit action, a preview, a summary) would silently diverge from what the user believes is selected. This is exactly the "else-branch coverage" anti-pattern this protocol requires checking for: one branch (success) is fully handled, the sibling branch (error) is under-handled.
   - Confidence: MEDIUM — a developer could partially object that the browser's native display text is outside the app's control; that's true, but it does not excuse leaving `selectedFile` un-reset, and the native display itself can be corrected defensively (see fix).
   - User group impacted: All users, not AT-specific — this is a state-coherence defect that happens to compound the accessibility gaps above (if `aria-describedby`/`aria-live` were fixed but this were not, a user could still be told "your file was rejected" while a *different*, stale file remains the app's actual selection).
   - Why this matters: WCAG 3.3.1 (Error Identification) requires that when an error is detected, it is identified and described to the user in a way that reflects the actual system state; a message that says "rejected" while the app quietly retains an unrelated prior selection undermines that identification.
   - Fix: On the rejection branch, explicitly reset the tracked selection (`setSelectedFile(null)`) and, if the native display needs to reflect the rejection, clear the input's own value (e.g., via a ref: `e.target.value = ''`) so the visible control and the app state agree.

**Minor Findings** (friction but workaround exists):

- No upfront disclosure of the 5MB size limit (or, beyond the `accept` filter, the allowed file types) anywhere in the visible UI before a user acts. `accept=".pdf,.doc,.docx"` (line 30) narrows the OS file-picker's default filter but is not a substitute for visible instructions, does not enforce size, and communicates nothing to a screen reader user beyond what the OS dialog itself exposes (which is separate from the page's own accessible tree). WCAG 3.3.2 (Labels or Instructions). *Recalibrated from an initial MAJOR read down to MINOR*: detection is immediate (the error fires right after selection) and a workaround exists (retry with a smaller file) — mitigated by: fast feedback loop and low cost of retry, even though every user who exceeds the limit is affected.
- The error message text itself ("File too large") never states the actual limit or a corrective path — a user who sees or hears it still has to guess how small is small enough. WCAG 3.3.3 (Error Suggestion). Fix: "File too large (max 5MB)."

**Enhancements** (best practice not met):

- axe-core also flags `landmark-one-main`, `page-has-heading-one`, and `region` (moderate/best-practice) against this page. These are properties of the test-harness page shell that renders the component in isolation (no `<main>`, no `<h1>`, no landmark wrapper) — `BuggyFileInput` itself is a fragment, not a page, and doesn't own page-level landmark/heading structure. Not scored against this component; would become a real finding only if the component is later embedded in a production page that still lacks these.
- The keyboard-a11y-tester trace measures the input's rendered bounding box at `width: 253, height: 21` (step_0001, step_0003) — the 21px height is under the WCAG 2.5.8 (Target Size, Minimum) 24×24 CSS-pixel threshold. No custom sizing CSS is present in the given source, so this is the browser's own default rendering of `<input type="file">`, which very likely falls under 2.5.8's "User Agent Control" exception (target size determined by the user agent, not modified by the author). Not scored as a violation; flagged so it is re-checked if custom styling is ever applied to this control.
- The "Upload file" text is a plain `<div>`, not a heading. If this component is meant to stand as its own page section (rather than a field inside a larger form with its own heading), a semantic heading (e.g., `<h2>Upload file</h2>`) would improve wayfinding — this is context-dependent and not scored without knowing the surrounding page structure.

- Missing defensive reset of `selectedFile` / native input value on the rejection path (Major Finding 2).

**Verdict Justification**: Two CRITICAL findings exist — missing label association and a silently-failing validation error — both independently corroborated by measured evidence (axe-core's critical-impact "label" violation; the census's empty live-region/ARIA-ref declarations) rather than code-reading alone. That rules out ACCEPT or ACCEPT-WITH-RESERVATIONS: a component that leaves screen reader users with zero signal when their upload is rejected is not shippable as-is. It does not warrant REJECT, however: the component's foundational choices are sound — a native `<input type="file">` with no ARIA-widget misuse, fully operable keyboard traversal, and a focus indicator that measures clean at both AA and AAA. The required fixes (label association, `aria-describedby` + live region on the error, `aria-invalid` wiring, the else-branch state reset, and upfront/corrective instructional text) are standard, narrow, and don't require rethinking the interaction model — hence REVISE. One recalibration is recorded: the "no upfront size/type disclosure" finding was initially considered for MAJOR but was downgraded to MINOR because detection is immediate and a low-cost retry workaround exists (mitigated by: fast feedback loop, low retry cost), consistent with the protocol's recalibration rule. Given the screen-reader perspective alarm is HIGH, this component would be a reasonable candidate for `/perspective-audit` escalation focused specifically on the screen-reader lens before re-review.
