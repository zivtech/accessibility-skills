# Fixture: Hybrid Product Evaluation Plan

## Feature Description

Lakeshore Mutual Credit Union needs a formal accessibility evaluation of everything its members touch, ending in a written report its compliance officer can hand to a county-government client and to the state regulator handling a member complaint. The complaint came from a member who uses a screen reader and could not finish a transaction dispute in the Android app.

The member-facing product is five surfaces:

- **Marketing site** — WordPress, about 30 pages: rates, product pages, a branch locator with an embedded map, blog, contact.
- **Online banking portal** — React single-page app behind login, about 60 distinct screens: login with SMS one-time codes, account dashboard, transfers between accounts, bill pay, payee management, statement downloads, secure messaging, card controls, transaction disputes.
- **iOS app** — native Swift/SwiftUI, not a wrapped website. Same features as the portal, plus check deposit using the phone camera.
- **Android app** — native Kotlin/Jetpack Compose, also not a wrapped website. Feature-matched with the iOS app.
- **Monthly statements** — PDFs generated by the core-banking vendor and downloaded from the portal. The credit union cannot change how the vendor generates them this year.

Members mainly log in, check balances, move money between accounts, pay bills, deposit checks with the phone camera, and dispute charges.

## Context

- **Compliance target named in the county contract:** WCAG 2.2 AA
- **Timeline:** report due in 10 weeks
- **Team:** 2 QA engineers, plus one front-end developer part-time
- **Existing tooling:** QA already runs the axe DevTools browser extension by hand on the portal and maintains a Playwright suite for the portal's main flows. The QA lead's working assumption is that this setup can be pointed at everything above, including both apps; there is no budget for new commercial tools.
- **Assistive technology:** some members use screen readers and screen magnification; the credit union has no data on which ones.
- **Build context:** the portal and both apps are built in-house from one shared design system; the PDFs come from the vendor.

## Requirement

Plan the evaluation. The plan should say:

- What you would examine on each surface, and why those parts and not others
- What method or tool applies where, and who runs it
- What the written report will contain when the evaluation is done
- What to tell the QA lead about the existing axe + Playwright setup
- How the 10 weeks and the 2 engineers get allocated

The compliance officer approves the engagement based on this plan, and they are not a technical reader.
